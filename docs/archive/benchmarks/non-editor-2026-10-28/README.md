# Coflow 0.14.0 非编辑器性能基线与优化报告

## 范围与结论口径

本报告评估 Rust 共享 Runtime、独立 CLI 与 C# Loader 的数据加载、查询、批量修改、成员变化、维度操作和错误处理。编辑器界面、前端渲染与 LSP 不计入本轮。C# 的两个目标宿主是 .NET 8 和 Unity Player；Unity Mono 与 IL2CPP 分别验收。

当前核心问题集中在三个层面：错误路径存在重复全量工作；正常局部修改与跨文件、成员变化的成本差距大；C# 加载及维度视图存在可减少的描述符扫描、对象重建和分配。本文中的优化预算是实施目标，不是已经完成的优化。本轮新增基准工具和文档，没有修改生产实现。

完整逐指标样本见 [measurements.md](measurements.md)，机器可读结果见 [summary.json](summary.json) 与 [summary.csv](summary.csv)。长期实施方案见[非编辑器性能优化方案](../../../development/non-editor-performance-plan.md)，测量约定见[基准协议](../../../development/non-editor-benchmarks.md)。

最终汇总收录 545 条带规模/参数的已完成耗时记录及 88 份进程状态；同一操作在不同夹具中的结果分别保留。超时、中断、准备失败与环境失败不进入完成耗时分布。正式 C# 覆盖 .NET 19 组与 Unity Mono 17 组，IL2CPP 保持未实测。

## 如何读这些数字

- Rust 热会话包含实际 API 调用及内部临时对象释放；CLI 包含新进程创建、完整事务、标准输出采集和退出；C# `load_text` 从已有字符串开始，不执行 CFT 编译、Rust 规则检查或磁盘发布。三者不用于计算语言实现的性能倍数。
- 加载及复杂操作通常为 3–5 个样本，仅报告算术中位数与范围。P95 至少 20 个样本、P99 至少 100 个样本才展示；它们仍是本次描述性分位数。查询批次除以操作数得到平均调用时间，不能解释为单调用尾延迟。
- 首次 Loader 调用包含实际加载及本进程首次执行/JIT 成本，不包含进程启动或机器冷启动。文件读取组使用可复用的 OS 缓存。重操作的主动完整 GC 协议用于固定结果生命周期，不代表实际应用自然 GC 下的连续吞吐。
- Rust/.NET/Unity 基准进程峰值包含夹具、预热、断言和历史分配。直接 CLI 内存探针只采样 `coflow.exe` 的加载、命令和输出。约 100ms 外部采样可能漏掉最后区间；峰值不是单个模型常驻内存。
- 超时是删失结果；中断运行、超时及准备阶段失败均单列。运行总墙钟不能直接记为某一 API 的完成耗时。没有样本的项目不填估计值。

矩阵基础夹具为 20 字段，含数组、字典、内联对象、Option、引用和模板；十万条/百文件输入约 31.79 MB。下表为已加载会话操作，除加载行外均不包含建立初始会话的成本。

| 新会话加载，不执行规则 | 4,457.68 ms | 3 | 同一数据夹具 |
| 修改 name（含模板传播） | 50.16 ms | 3 | 重建 2 条，复用 99,998 条；重读 1 文件 |

| 跨 100 文件的 1,000 项修改 | 6,265.12 ms | 3 | 重读 100 文件，检查 100,000 条身份/来源 |
| 新增记录 | 6,645.65 ms | 3 | 100,001 条完整重建 |

这说明字段增量已经有效，但收益受来源文件布局和成员变化限制。跨文件批次的模型重建仅约 1,100 条，端到端仍达秒级，后续需要分开测候选文本、完整解析、来源/身份访问和实际文件发布；单纯继续缩小模型求值集合不足以覆盖全部成本。

历史 `engine_perf` 的既有 54.27 MB 复杂夹具另外复测：十万条连续修改 100 样本 P50 为 42.01 ms、P95 为 51.48 ms、P99 为 58.99 ms；加载 3 样本中位数 11,559.29 ms。该夹具与新矩阵内容不同，不能相除得到优化倍数。该轮绝对热编辑分位数满足既有 50/100 ms 预算，但只有单轮同版本复测，不能据此宣称完成了“相对绑定基线改善至少 25%”的稳定验收。

新矩阵另外采集 100 个热样本：修改 name（含模板传播）的 P50/P95/P99 为 52.25/62.50/68.57 ms，修改 value（含规则依赖传播）为 54.74/62.45/70.42 ms。前者 P50 仍略高于 50 ms。完整无变化文件刷新为 24.29/29.81/33.27 ms，不能与只校验相同内存文本的微小耗时混为一谈。

| 专项 | 实测中位数 | 解释 |
| --- | ---: | --- |
| 万条单文件，修改单字段 | 191.86 ms | 文件布局扩大来源/文本处理成本 |
| 万条单文件，同文件 1,000 项 | 438.74 ms | 健康单文件在结构预算内 |

| 千条，数组长度 1,000，加载 / 修改一个元素 | 2,423.33 / 67.59 ms | 长集合容量专项 |
| 万条，两维各 10 变体，稀疏 / 密集加载 | 2,058.31 / 3,570.13 ms | 每维覆盖率分别 1% / 100% |
| 上述稀疏 / 密集维度值修改 | 15.52 / 17.12 ms | 已有会话的单值修改 |
| 上述稀疏 / 密集清除覆盖 | 6.15 / 7.80 ms | 删除显式覆盖 |

表中维度写入/清除操作专用 `language[bench]` 变体的小文件 `bench.cfd`；稀疏/密集区别来自已加载背景数据，不能据此推断修改大型 `variants.cfd` 的成本。`dimension_lookup` 只查显式覆盖，不表示整模型投影；完整投影使用独立 `engine_perf` 模型专项。宽度、布局、模板和维度不同的矩阵只按各自规格解释，不能把多个同时改变的因素归因于其中一项。

已有覆盖文件专项直接修改 `language[v0]` 中 `r000000.name`，目标为 `dimensions/language/variants.cfd`，其余条件仍为万条、两维各十变体。每项 3 个正式样本，每次修改后独立重载，核对全部基础字段及两维所有变体的覆盖状态；逐次恢复后核对会话覆盖状态，最终再独立重载复核恢复结果。

| 已有覆盖文件 | 修改一个值 | 清除一个覆盖 | 修改样本的工作量 |
| --- | ---: | ---: | --- |
| 稀疏：41,050 B，1,000 个覆盖 | 53.59 ms | 57.13 ms | 检查 1,000 个维度输入，求值 18,000 个根字段 |
| 密集：4,089,070 B，100,000 个覆盖 | 3,738.05 ms | 3,847.48 ms | 检查 100,000 个维度输入，求值 900,000 个根字段 |

清除组通过公共 API 逐次恢复原值，格式差异使三个正式样本开始时文件比表中初始值分别增加 9/17/25 B；实际字节数逐样本记录。计时包含清除及发布，恢复和正确性复核在计时外。两组都只发布一个文件。密集场景表明，单个覆盖修改仍会触发大范围维度输入校验和求值；小文件写入结果不能代表这一容量路径。后续需按实际变化覆盖及依赖闭包收窄处理，并单独测量整个覆盖文件解析和发布成本。

### 底层模型与完整维度投影

`engine_perf` 模型专项将输入和 schema 构造放在计时外，只测模型构建或投影，每项 3 个样本。万条模型、8/32/128 字段的构建中位数分别为 19.18/81.75/415.41 ms。每样本执行 10,000 次共享快照 clone/drop 约 0.75–0.77 ms；这是不可变数据共享，不是深拷贝。

完整维度投影夹具为单维、8 字段、相邻引用环，模板读取 `parent.name`。万条从基础模型首次选择一个变体的耗时如下：

| 已声明变体与覆盖率 | 首次完整投影 |
| --- | ---: |
| 1 变体，稀疏 1% | 113.17 ms |
| 1 变体，密集 100% | 114.59 ms |
| 10 变体，稀疏 1% | 100.82 ms |
| 10 变体，密集 100% | 78.89 ms |

当前投影遍历全部记录，将值重新转成草稿、重新解析格式模板、构建模型并复制维度元数据，因此稀疏覆盖仍承担完整重建。三个样本中密集十变体更快不能推导为普遍规律。对已有投影重复相同选择仅返回共享快照，测值接近计时器开销，不作为纳秒级时延保证。本专项未测十万条完整投影或两维组合。

独立小文本 parser 探针在两次进程中的中位数范围：健康 100/1,000/5,000 条分别 0.025–0.124 / 0.252–0.411 / 1.300–2.562 ms；缺值错误 100/1,000 条分别 0.059–0.116 / 0.574–1.230 ms，产生对应数量的诊断。两次使用相同文本，保留各自样本，不合并为规模对照。该探针不含 Runtime 来源定位或部分模型重建，不能替代下文 P0 错误路径的结论。

| --- | ---: | --- |

这些结果用于暴露宽字段、文件布局和变体数量带来的事务成本，不代表稳定长尾。优化前后需按相同产物生成方式、配置和输入重复测量；不能把两次不同二进制摘要的单轮样本当成优化配对。

源码审查确认了三类可独立实施的优化；当前没有阶段剖析数据，不能为它们分配精确耗时百分比：

1. **逐记录的路径和配置工作。** 前后基础快照对每条记录调用 `unshadow`，其内部重新解析 YAML、构造源根、执行文件系统路径规范化。固定源根和文件布局下，这是高常数 O(N)，可按事务和唯一文件缓存。它能解释为何同值写入和预览仍远慢于只读查询。
2. **全量语义表示。** 前后快照都遍历基础记录和每个已声明单变体，构造完整记录 DTO，再转 JSON/反序列化并生成差异状态。当前两个变体还带来四次完整模型投影。应使用共享的类型化状态、受影响闭包和按需细节输出，保留完整差异计数与间接模板变化。
3. **CLI 批次逐项处理整个文件。** CLI 每项新建 Writer、复制源文本、解析旧文/候选、写临时候选，再刷新整个文件索引。Runtime 的字段批次已经合并，CLI 尚未使用等价聚合路径。只对顺序和前置条件可证明独立的操作分组；创建、删除、重命名、数组索引变化等顺序敏感边界必须保持。

还可减少输入字节克隆、重复修订哈希、无诊断时的来源集合分配和“每记录扫描全部变化字段”的差异计数。路径映射和安全批次聚合适合先独立交付，再推进共享候选代次。

| --- | ---: | ---: | ---: | ---: |
| 1,000 条 | 采样不足 | 采样不足 | 134.76 MB | 140.58 MB |
| 10,000 条 | 240.79 MB | 240.41 MB | 1,200.06 MB | 1,206.96 MB |

## .NET 8 加载、访问与内存

C# 是只读 Loader，数据修改由 Rust/CLI 承担。C# 的“重新加载”创建独立上下文，并非增量更新已有业务对象。表中 MB 使用十进制字节，时间及两列内存分别取各自样本中位数。操作分配为 `GC.GetTotalAllocatedBytes(true)` 的进程托管分配差；保留增量是结果存活、校验后完整 GC 相对操作前的堆差值。它包含校验影响，基线已含输入字符串，不能等同于单模型对象图大小或进程峰值。

每个源字段校验及字段首次读取（缓存未命中）会线性扫描描述符，字段查找部分存在 O(N×F²) 工作；字段读取缓存命中提前返回。表构造还对每种类型遍历全部记录，存在 O(N×T) 扫描。当前多表基线没有表现出灾难性增长，仍应通过比较次数确认改动收益。解析 AST、逐记录 Reader 字典、值缓存装箱和视图状态使分配/保留成本远高于最终业务标量本身。

可先共享描述符名称索引与字段槽位、按类型及祖先预分桶，再针对分配剖析减少重复字符串、字典和装箱。文件读取加加载、保留旧结果时重载与错误恢复分别保存在完整明细，不能将 OS 缓存可用的 I/O 组解释为真实磁盘冷读。

C# 单文件十万条结果仅说明当前 Loader 对这份字符串的加载表现，不证明 Rust 项目解析/修改链支持同样的单文件布局；两者的结构限制必须分别验证。正式项目容量目标仍需同时满足生产端和消费端的限制。

带模板的 C# 夹具中，每条 `label` 都读取 `r0.name`，而稀疏覆盖包含 r0。因此 1% 显式覆盖也可能影响全部记录的标签；不能把覆盖率直接当作受影响记录比例。稀疏优化必须按实际依赖闭包处理，并通过关闭模板的对照区分全局依赖成本与重复构造成本。

关闭模板的控制组已完成：万条、两维各十个稀疏变体，.NET 加载中位数仍为 **7,938.34 ms**，分配 **3,319.52 MB**，GC 后保留增量 **110.01 MB**；Mono 为 **7,191.10 ms**，每组 3 样本。同配置带模板组分别为 8,044.60 / 7,814.85 ms。关闭模板后高成本仍存在，结合逐变体全量构建的源码路径，支持优先减少重复校验视图构造；这不是阶段剖析，不能据差值给各热点分配耗时比例。

万条、两维各一变体、稀疏覆盖的 .NET 维度缓存已经给出明确分配证据：每 10,000 次缓存 `For` 分配 7.36 MB，约 **736 字节/次**；未知变体缓存回退约 744 字节/次；`Variants` 约 224 字节/次；`HasVariant` 约 120 字节/次。`For` 返回缓存业务对象，但仍重建选择字典和键；`Variants` 创建列表包装，返回布尔值的 `HasVariant` 则包含捕获字段名的查询谓词分配。优化目标应同时限制耗时与分配，不能仅凭对象身份复用判断缓存已经足够便宜。

`loading/load.rs` 的 `build_partial_model` 每轮剔除失败记录并重新构建剩余全部候选。环内模板读取前驱/后继字段时，剔除一条会使下一条模板引用失败，累计处理量可接近 N+(N−1)+…+1。最后成功轮的统计没有覆盖失败轮工作量。普通可编辑缺失引用诊断不一定进入此路径，因此问题不是“所有引用错误都会平方退化”。

### 结构预算拒绝与诊断位置映射

Rust 默认每个 CFD 文件最多 1,000,000 个语法节点。当前复杂夹具每条 59 节点，单文件完整接受上限为 16,949 条；该记录数只适用于这份夹具。十万条单文件不属于该夹具的健康容量；探针进程在总墙钟 744.9 秒后中断，没有完成的加载样本，该时间不是加载 API 的测量结果。其环形模板截断还会叠加前述级联问题。

独立星形、关闭模板的预算拒绝探针排除了该级联：20,000 条单文件保留 16,949 条，产生 3,051 条结构超限诊断，单样本耗时 **47,067.53 ms**。错误诊断映射仍调用从文件头扫描的 `byte_range`，而正常来源已有行索引；大量错误形成“诊断数 × 源码长度”的重复工作。优先复用 `LineIndex`，保持所有诊断的代码、顺序和位置，再审查预算耗尽后的扫描方式。提高上限不能替代优化拒绝路径。

同值/预览和安全千项批次使用上表之前的专项预算；各操作仍分别保留实际影响数量和正确性结果，不能用族内较快操作代替较慢操作通过。恢复预算只适用于工具的局部错误夹具，模板级联与节点预算拒绝按 P0 专项验收。内存目标除已给出的 C# 分配/保留预算外，先要求各自口径的峰值不回归超过 5%，再由阶段分配剖析设定削减量。

先交付错误拒绝和 CLI 配置/路径缓存，再推进 C# 基础加载与 Runtime 局部工作；它们可独立实施和回滚。CLI 安全批次可在一般事务重构前交付。成员增量、共享候选代次和维度依赖校验属于较大改动，必须按独立阶段保存前后证据。各项源码依据、设计约束和测试清单见[完整优化方案](../../../development/non-editor-performance-plan.md)。

## 覆盖边界与复验要求

- 规模以千条、万条、十万条为主；字段宽度覆盖 8/20/100，底层模型专项另含 32/128。引用包含 Rust 全环/高扇入、CLI 二叉树/高扇入、C# 无引用/成对/64 条独立环/高扇入。不同入口的夹具不相同。
- Runtime 矩阵覆盖 32 项常见操作，另有结构预算拒绝和已有覆盖文件专项；CLI 覆盖工具列出的 39 项操作。C# 覆盖文本/I/O/重载、查询、类型/语法/引用拒绝与恢复，以及维度首次/缓存/组合/回退。覆盖表示有明确测试入口和实际结果记录，不表示全部场景性能达标。
- Rust/C# 的 `variants=10` 表示两维各 10 个，总计 20；CLI 为语言 10 个加平台 1 个，总计 11。C# 两维组合测试不穷举所有变体的笛卡尔积。
- 本轮没有百万条、超内存、网络盘、机器冷缓存、移动设备、WebGL、真实游戏帧、持续数小时缓存增长或多线程争用的实测；没有独立的 C# 超 256 层长链拒绝基准。CLI 长集合/长字符串、多表继承、零维度/无引用对照也未覆盖。性能结论不向这些边界外推。
- 大多数加载和 CLI 操作样本不足以评估稳定 P95/P99。系统后台任务、功耗和温度没有做实验室隔离；不同时间段和宿主的单轮差异不能作为通用速度排序。优化前后应固定工具和输入，至少三轮交替复测。
- 正确性复验包括全部基础值、引用身份、维度结果、独立重载及未发布输入保持。目标阶段还须补齐旧快照、诊断顺序/Unicode 位置、执行预算、冲突和发布回滚测试；完整清单在优化方案中。
