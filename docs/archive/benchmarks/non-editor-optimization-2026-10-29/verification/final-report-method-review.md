# 最终性能报告口径独立审查

审查范围为 `summarize.mjs`、`compare-optimization.mjs`、`audit-optimization.mjs`、`report-optimization-targets.mjs` 与 `report-cli-memory.mjs` 的静态实现、冻结计划和原始预算。最终证据集合采用 Rust／模型／CLI R4 与 C#／Mono R6；正式结果已经汇集到 `final-results` 并完成逐项目标登记。本审查提供报告的证据使用规则。

## 证据分层

| 输出 | 可支持的结论 | 必须保留的边界 |
| --- | --- | --- |
| `summary.json`、`measurements.md` | 已保存样本的描述性统计 | 汇总器检查样本和 CLI 操作正确性；进程已退出即可读取输出，不以整个运行成功作为所有行的前提。 |
| `comparison.json`、`comparison.md` | 每进程中位数及同名场景、同轮操作的描述性比较 | 比较器本身不校验进程退出成功、完整夹具摘要或审计状态。表中的配对轮数不能直接充当验收通过轮数。 |
| `audit-final` | 参数、夹具、归档产物摘要、样本完整性、完成标记及串行区间审查 | `completed_pairs` 与 `partial_pairs` 分别统计；`complete_with_censored_or_failed_runs` 表示审计已完成但存在截尾／失败运行。 |
| `target-status.json`、`target-status.md` | 数值预算的逐条件验收 | 绝对目标要求至少三个成功优化进程；相对目标要求至少三对有效同轮同夹具进程。失败、截尾、缺失和空计数保持证据不足。 |
| `cli-memory-report.json`、`.md` | 四项独立 CLI 命令的峰值内存验收 | 使用直接 `coflow.exe` 进程的三对峰值；不使用 Node 驱动峰值代替。 |

目标报告独立重读原始样本，但不消费审计报告的判定。最终发布的目标结论同时要求相关审计检查通过。原始比较中存在而验收表排除的值可以用于说明观测情况，须同时标明排除原因及有效配对数。

## 最重要的报告约束

1. **保留失败与截尾。** CLI 驱动可在一个操作失败后继续运行。`correctness=passed` 的其他操作可以形成局部证据；失败操作即使保留计时样本也不进入成功统计。完整进程有失败／超时时，目标工具保守排除该进程，不以局部成功补足正式验收轮数。审计中的 `partial_pairs` 单独展示。
2. **超时时限不替代操作耗时。** 外部时限覆盖夹具准备、预检、预热、操作和校验；错误恢复尤其可能在准备非法状态时已经超时。优化侧的绝对目标可在三次成功测量后独立达标，缺少基线完成样本时，相对收益保持未验证。不能用外部 120 秒时限除以优化耗时计算倍率。
3. **相对值采用同一组有效配对两侧的中位数之比。** 每轮比例保留用于检查方向和波动。整体比例不等于每轮比例的平均数或中位数，也不表示每轮都改善。`comparison` 的总体值可能使用数量不同的两侧观测；主报告的验收比例使用 `target-status.criteria` 中的有效配对统计。
4. **样本单位明确。** 常规汇总是各独立进程中位数的算术中位数。慢操作每进程一个样本、三轮合计三次操作观测，不能称为有可靠 P95/P99 的分布。每进程至少 20 个原始样本才产生观察 P95，至少 100 个才产生观察 P99；目标 P95 为各进程观察 P95 的中位数。查询批次均值不等于单调用尾延迟。
5. **内存口径分别报告。** 托管分配、GC 后保留增量、进程工作集峰值各自有独立单位和边界。Mono 不支持的分配计数维持 `null`；零分配验收要求每条原始优化样本均为零。汇总器内存列属于便捷描述，严格验收使用目标工具对全部原始计数的完整性检查。
6. **峰值属于对应进程。** Runtime／模型／.NET／Mono 峰值包含宿主、夹具、预热和验证。CLI 独立内存报告预期 24 个被采样命令进程、12 份夹具复核、四项操作各三对；绝对上限为万条 set／batch 500 MB、十万条 get／check 1.2 GB，相对上限为 1.05。MB／GB 使用十进制字节。OS 累计峰值约每 100 ms 观察，退出末段可能缺测；此指标不证明常驻堆或单操作分配量。
7. **最终版本和补测证据分别登记。** `final-results` 只汇集 R4 原生／CLI 与 R6 托管原始文件，以逐文件来源、字节数、SHA256 绑定；只纳入对应版本的计划，保持每个场景／轮次／臂唯一。旧托管结果、校准和 `stability-r4` 分别列出，不能混入正式三轮、替换较慢轮次或用于补足缺失配对。复制保持原规格和时间；来源目录改变不改变样本身份。
8. **达标条件逐条保留。** 一项目标可能同时包含耗时、分配、保留内存、相对改善或 P95。某一条件通过不表示整项通过；任一条件未达标，整项目标仍未达。条件回归预算中 `not_applicable` 只表示该稳定性条件的基线前提不成立，绝对预算继续独立判定。
9. **数值预算与 G1–G13 机制目标分别验收。** `target-status` 的目标数量不是“所有优化计划全部完成”的分母。G1 的零工作量、G3 的相同变化文件下模型阶段斜率、G4 的一次候选／验证、G6–G9／G11／G13 的累计工作量或复杂度，需引用计数、阶段计时及对应回归。G7 仍为部分实现；完整不可变输入／候选代次共享及按受影响集合差异仍属于剩余工作。端到端提速不自动完成这些证明。
10. **功能和宿主结论分别陈述。** Rust 基准恢复夹具后的完整重载标志验证的是恢复后的状态；变更态、旧快照、诊断顺序、预算和原子发布能力由相应专项回归证明。C#／Mono 已测结果不能替代 IL2CPP；未取得真实 IL2CPP Player 的构建、裁剪、语义和性能证据时，该宿主保持未验证。文件缓存、调度和功耗未受控，本机三轮数据属于描述性结果。
11. **进度与样本记录分离。** `sample_started`／`sample_completed` 只记录阶段进度，不参与聚合指标唯一性检查。真实重复指标、未知事件和缺失 `samples_ms` 仍拒绝，见[分析回归验证](report-progress-event-regression.json)。多个计划对同一 ID 的引用只在规格完全相等且指向同一来源文件时去重；全部计划保留，一个进程只计一次。

## 万条 CLI 基础矩阵覆盖

冻结的 `cli-common-10k` 计划为 10,000 条、10 文件、20 字段、语言／平台各一变体，选择 8 项操作：`data_get`、`check_rules`、`set_field`、`set_field_rules`、`set_noop`、`set_preview`、`batch_same_file`、`batch_cross_file`。批次预算绑定实际 1,000 项。

其余 31 项基础预算固定绑定 `cli-expanded-10k`，通过 `optimization-suite.mjs --extended-cli true` 显式启用补采；沿用冻结 R4 二进制、不变的 `cli-matrix.mjs` 和同一基础夹具，`set_where` 采用实际 1,000 项。该场景不加入默认套件，也不修改已有 common 计划。六个进程全部完成，以下每项均有三对成功样本：

| 操作族 | 扩展补采操作 | 数量 |
| --- | --- | ---: |
| 工程与 Schema | `project_inspect`、`schema_inspect` | 2 |
| 一般读取与检查 | `data_list`、`filter_sort`、`data_search`、`stats_field`、`check_structure` | 5 |
| 引用 | `data_refs` | 1 |
| 维度读取 | `dimension_get`、`dimension_missing`、`dimension_diff`、`dimension_query` | 4 |
| 集合与成员等修改 | `array_insert`、`array_remove`、`array_move`、`dict_set`、`dict_remove`、`create_record`、`delete_record`、`rename_record`、`transfer_record`、`unset_field`、`dimension_set`、`dimension_clear`、`source_write` | 13 |
| 新变体 | `dimension_add_variant` | 1 |
| 条件批次 | `set_where`，要求实际影响 1,000 条 | 1 |
| 拒绝与恢复 | `reject_invalid_value`、`reject_invalid_source`、`repair_invalid_source` | 3 |
| 冲突 | `revision_conflict` | 1 |

万条基础矩阵共 39 项操作均已取得三对成功样本，完整结果见[最终结果表](../results-tables.md)。千条同名操作、十万条专项和万条十变体专项仍有各自的证据范围，不将完整基础矩阵外推为全部规模与参数组合。

## 最终登记方式

主报告分别列出数值目标状态、过程峰值状态、四项 CLI 内存状态、G1–G13 实现／证据状态与宿主覆盖。每项重要收益同时给出场景、样本单位、三轮范围、有效配对数和原始证据链接。未达标与未验证项目按原因分别归入剩余计划：实现成本、数值预算、缺少阶段证据、缺少操作覆盖或宿主不可用。

最终分析工具按上述分工使用即可保持失败、缺失与空计数的可见性。补采只增加显式启用的场景和相应目标的固定证据归属，原始基准驱动、统计口径与数值预算保持一致。
