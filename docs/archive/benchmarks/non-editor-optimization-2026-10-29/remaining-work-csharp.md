# C# 下一阶段的内存与宿主验收

本表区分已实现机制、需要堆分析确认的成本占比与尚未完成的宿主验收。正式耗时、分配、保留内存及目标状态统一以 `final-results/target-status.json` 和 [最终比较](final-results/comparison.md)为准。功能等价、回退边界与数值预算分别验收；对象数量不能直接换算为经过测量的独占字节数。

## 已实现与功能验证

| 机制 | 当前实现 | 功能验证 |
| --- | --- | --- |
| 根语法包装回收 | RecordState 只保存不可变 ID、类型、位置与路径；Reader 保留求值所需源节点、覆盖和表达式，根 Record、Field 及 Fields 列表可在槽位建立后回收 | WeakReference 验证包装可回收，回收后首次组合视图、默认嵌套模板与循环引用身份仍正确；保留身份、单例、覆盖和字段的原序首错 |
| 无类型 ID 索引 | 每 ID 直接保存唯一记录或持久歧义状态；按继承根和 ID 的限定索引独立保留 | 一、二、三根同 ID 及限定引用结果正确，第三条记录不会使歧义状态恢复为唯一 |
| 引用与深构造恢复 | 普通 Reference 及 Option／Dimension 包装通过显式 DFS 记录栈调度，逐包装保持常量解析；复杂读取在异常第一遍搜索时由筛选器登记暂停身份与槽位，调度器统一恢复 | 32 层原生调用段及 256 层逻辑限制保持；默认线程的深引用、深模板、混合路径、待完成父字段循环、集合一次构造与深度优先错误顺序通过 |
| 普通表查询 | 热查询直接访问加载器独占的具体 Dictionary，Keys／Values 保持只读包装；字典按原容量增长，保留 CLR 类型分桶 | 缺失／null 键异常、只读集合、枚举及记录身份一致 |
| 名称哈希 | 两个 UTF-16 码元无损打包，连同长度交给随机 HashCode；最终以完整 Ordinal 比较判等 | 奇偶长度、代理项、NUL 与不同 Unicode 表示保持精确区分；仅字段名与类型名进入本次加载的名称池 |

[R6 构建与烟测收据](verification/csharp-r6-build-smoke.json)记录 C# Release **86/86 通过**、netstandard2.1 烟测及生成代码／共享语料集成通过。Unity 2022.3.62f3 Mono Player 的 scalar8、scalar20、scalar100、tables32、complex、dimensions 六类烟测通过，主线程及默认新线程各 15 项契约检查，共 **30 项通过**；这些检查没有产生正式性能样本。

## 剩余成本与验收

| 优先级 | 已确认的成本 | 下一步实现与分析 | 功能保持条件 |
| --- | --- | --- | --- |
| 1 | Reader 同时保留源值节点、解析结果 `object[]` 和状态数组；标量结果装箱，业务对象另存强类型字段 | 在加载完成、结果存活、完整 GC 后采集堆快照；量化根包装回收和唯一／歧义索引的节省，再剖析数字文本、ScalarValue、装箱及数组占比，决定紧凑标量表示和减少装箱的具体实现 | 保留模板、引用和常量别名后续求值需要的表达式；独立核对累计分配与保留内存，不直接释放所有源节点 |
| 2 | 内联 Reader 缓存和深构造暂停容器存在于对应 Reader | 确认复杂夹具中的保留链，评估构造完成后释放空暂停容器及压缩内联缓存 | 保留 32 层原生调用段、256 层逻辑限制、深度优先错误顺序、循环引用身份和集合元素只构造一次的语义 |
| 3 | 选择、转换和已交付视图缓存随业务访问保留，加载预校验视图已经移除 | 增加长期组合访问及释放后的生命周期测量，量化选择表示和单个业务对象对整个加载上下文的保留链，再评估压缩表示 | 已交付视图的引用身份、组合顺序无关、上下文隔离与并发锁保护保持一致；缓存淘汰策略需独立产品决策 |

主要实现位置为 [Loading.cs](../../../../runtimes/csharp/Coflow.Loader/Loading.cs)、[Dimensions.cs](../../../../runtimes/csharp/Coflow.Loader/Dimensions.cs) 和 [Construction.cs](../../../../runtimes/csharp/Coflow.Loader/Construction.cs)。名称池、解析器和文档容器本身不是当前长期保留链；字段及类型名称已经共享。堆分析须区分对象的独占大小与共享引用，不能重复计费。

所有改动继续要求 Load 返回前完整验证全部已声明单变体。阶段结果分别报告累计分配、完整 GC 后保留增量和进程峰值，不互相替代。

Unity Mono 当前的逐操作分配计数不可用，`null` 保持未验证。下一步需要实际 Player 的分配分析和堆快照，并独立覆盖真实帧、长期缓存与多线程争用。现有结果只对应非 Development、关闭增量 GC、关闭托管裁剪的配置。

Unity IL2CPP 的同版官方模块下载仍返回 HTTP 404。取得模块后需要独立验证 AOT、裁剪、默认线程深度契约，再采集同夹具的成对耗时与内存；.NET 和 Mono 结果不替代此项验收。

## R6 正式结果边界与后续优先级

R6 托管矩阵的 **144/144 个独立进程完成**，覆盖两宿主、24 个场景和三轮前后配对；[结果审计](verification/managed-r6-audit.json)没有失败、部分结果或审计问题。正式耗时及逐轮来源见 [managed-r6 比较](managed-r6/comparison.json)、[汇总](managed-r6/summary.json)及同目录原始 NDJSON。全项目汇总归入 [final-results](final-results/comparison.md)，最终目标状态以 `final-results/target-status.json` 为准。

已测的表查找／枚举与 24 组进程峰值通过既定回归门槛。加载、重载、恢复及 Loader 拒绝路径的稳定性目标中，仍有下表两项 Mono 拒绝未通过；稀疏维度的更高改善目标与普通属性读取也有缺口。**共有七项目标未达标，不能将本轮结果表述为所有回退均已消除。**

| 场景／操作 | 基线 → R6 | 目标状态 |
| --- | --- | --- |
| .NET dim1 sparse 10k 加载 | 896.898 → 389.973 ms，降低 56.52% | 未达到降低至少 60%；累计分配降低 68.23% 的子目标已通过 |
| Mono dim1 sparse 10k 加载 | 1286.138 → 535.505 ms，降低 58.36% | 未达到降低至少 60%；逐操作分配仍无计数证据 |

| .NET width8 10k 属性读取，每万次 | 0.01870 → 0.02015 ms，增加 1.45 µs／批 | +7.75%，超过 5% 回归界限 |
| .NET tables32 10k 属性读取，每万次 | 0.02510 → 0.02755 ms，增加 2.45 µs／批 | +9.76%，超过 5% 回归界限 |

### 三轮 GC 关联

Mono 两项拒绝在每轮的基线计时区间均为 0 次 GC，R6 均为 1 次。原始记录分别为第一轮[基线](managed-r6/mono-dim1-sparse-10k-r1-baseline.measurements.ndjson)／[R6](managed-r6/mono-dim1-sparse-10k-r1-optimized.measurements.ndjson)、第二轮[基线](managed-r6/mono-dim1-sparse-10k-r2-baseline.measurements.ndjson)／[R6](managed-r6/mono-dim1-sparse-10k-r2-optimized.measurements.ndjson)、第三轮[基线](managed-r6/mono-dim1-sparse-10k-r3-baseline.measurements.ndjson)／[R6](managed-r6/mono-dim1-sparse-10k-r3-optimized.measurements.ndjson)。每项每进程只有一个计时样本，GC 计数在操作后、样本后的强制回收前取得。

三轮 R6 托管堆保留容量均为 425.86 MB，基线分别为 962.52、912.40、996.29 MB。完整 GC 后，R6 未知类型拒绝的托管存活量为 298.16—298.22 MB，语法拒绝为 285.39—285.65 MB；这些指标包含宿主、夹具和历史加载对象。较小的保留堆与额外 GC 同时出现，但未采集 GC 耗时，尚不能确定约 51—52 ms 汇总差额中各阶段的占比。已观测的端到端回退继续保留，不通过预扩堆、改变 GC 配置或移出计时区间来改写本轮结论。

### 属性读取的代码与测量边界

[R6 驱动审计](verification/csharp-harness-audit-r6.json)确认两版基准的 847 个方法 IL、局部变量和异常区域完全相同，53 份源码校验一致，包含生成属性、适配器与测量循环。`direct_property_batch` 在计时前取得同一条记录，计时内执行 `data.Value(row)`、类型转换与生成的 `f0` 属性访问；该路径不访问 Table 字典、Reader 或构造调度器。

三个未达场景的两版本、三轮共 1,800 个原始批次均记录为零分配、零 GC。width8 三轮均变慢；scalar20 100k 与 tables32 第一轮较快、后两轮较慢。代码一致不证明 JIT 产物、分层编译状态、缓存或对象布局一致，当前证据也不足以将差异直接判作噪声；三项目标仍按既定 5% 界限登记未达标。

### 后续验证顺序

1. **Mono 拒绝路径：**在独立诊断运行中采集 GC 耗时、触发前托管堆及分配热点，分开计量解析与身份登记。优先减少临时对象和重复工作，验收保持真实宿主 GC 行为、原计时边界、诊断位置及首错顺序。
2. **单变体稀疏加载：**分别剖析基础解析、覆盖登记和完整单变体校验的剩余时间，按最大实际占比继续优化；全部已声明单变体仍须在 Load 返回成功前验证。按原配对协议同时验收降低至少 60%、内存与失败路径。
3. **.NET 属性读取：**先以独立诊断确认 JIT 分层／PGO、生成机器码和适配器调用开销，再增加相同产物、相同计时边界的独立进程配对。保留现有三轮原始结果和 5% 门槛，避免根据微秒级差额直接改动未证明存在额外工作的属性代码。
4. **宿主证据补齐：**另行取得 Mono 分配分析和 IL2CPP 实际 Player 验收，并覆盖长期缓存及真实游戏帧；已通过的 .NET 指标不补齐这些缺测项。
