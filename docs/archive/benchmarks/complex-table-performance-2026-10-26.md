# 复杂表格滚动专项采样

日期：2026-10-26。测量对象为工作区生产构建，基于 `f310934c4ada174b84be0e2f94aed22428c2d7e1`，包含当前预览对齐、取消选中、下拉关闭与引用图标修改。正式渲染组件保持原状；本次新增参数化夹具和采样脚本。

## 环境与方法

Windows、Intel Core i5-13600KF、32 GiB 内存、无头 Chromium 156.0.8078.4，Vite 生产构建。浏览器视窗 1280×800，表格区域 880×480，3,000 条记录、20 个业务字段。复杂列位于末尾，纵向采样保持横向滚动位置为零；即使位于横向视口外，复杂列也参与挂载。

每个场景先纵向、再横向采样。场景顺序正向、反向各一轮，测量期间无并行构建或回归测试。每轴最多 90 次动画帧，重场景达到 8 秒时结束，舍弃最初 4 个帧间隔。每轮实际保留 27–85 个帧间隔；P95 是该轮观测分位数，两轮范围不构成稳定尾延迟保证。纵向每动画帧前进 120px；横向按 60 步遍历滚动范围。

数组元素为含 Label、Count、Nested 三个字段的对象；嵌套场景只增加 Nested 内部层数，子项保持折叠。对象场景为每个对象直接包含 8 个字符串字段。测试沿用合成数据的跨记录值共享，不包含真实后端 IPC、磁盘、插件、引用显示名查询或实际用户数据。DOM 统计为各场景回到顶部、完成横向采样后的挂载量，不代表滚动中的峰值。

原始结果：[正式构建采样](complex-table-performance-2026-10-26.json)、[跳过摘要测量的诊断构建](complex-table-performance-no-summary-2026-10-26.json)。所有场景均无页面异常。

另有 12 列数组的[CPU 归档轮及补充计时](complex-table-cpu-2026-10-26.json)、[原始 CPU profile](complex-table-cpu-2026-10-26.cpuprofile)。补充两轮纵向 P50 均为 250ms，P95 为 283.3–299.9ms，横向 P95 为 50.0–50.1ms。它们与主采样的尾延迟存在明显差异，说明重场景分位数仍受采样轮次影响；全部观测均保留，严重掉帧的判断以持续高于帧预算的中位数和布局工作量共同支持。

## 摘要测量的诊断对照

诊断构建通过 Vite 源码覆盖，仅跳过 `StructureSummary` 的初次宽度测量及其 ResizeObserver、MutationObserver、字体监听注册。正式组件文件没有修改。此构建用于归因；它不再按宽度隐藏摘要片段，不能作为保留原有显示行为的优化实现。

| 场景 | 正式纵向 P95 ms | 诊断纵向 P95 ms | 正式 LayoutDuration ms | 诊断 LayoutDuration ms |
| --- | ---: | ---: | ---: | ---: |
| 2 列数组，每格 8 项 | 50.0–50.1 | 33.4 | 941.2–944.2 | 127.0–127.2 |
| 12 列数组，每格 8 项 | 550.1–583.4 | 266.7–300.0 | 3,165.8–3,202.3 | 309.0–310.4 |

两列场景正式与诊断均为 85 个有效帧间隔，DOM 数量一致，布局累计耗时减少约 86.5%。12 列场景受 8 秒上限影响，正式主采样保留 27–29 帧间隔，诊断保留 62–63 帧间隔，累计耗时应结合不同的工作量解释。两轮诊断纵向 P50 为 133.2–133.3ms，仍显著超过单帧预算；减少布局测量不能单独解决全部卡顿。12 列场景横向 P95 在诊断构建中仍为 100.1–116.6ms。补充正式构建的 P95 与诊断结果存在重叠，摘要测量的归因以两列对照、布局耗时及 CPU 调用来源为主要证据，不将重场景单轮 P95 差异视为稳定收益。

## CPU 热点

正式构建的 12 列数组场景在独立纵向滚动轮执行 V8 CPU profiler，不将采样轮帧间隔混入计时结果。归档 CPU profile 的 6,628 个命中样本中，`getBoundingClientRect` 命中 2,583 个，占 39.0%；这是采样命中占比，不等于端到端墙钟耗时占比。

四个主要 `getBoundingClientRect` 节点合计命中 2,583 次。核对生产包对应位置后，调用来源均为 `StructureSummary.measure` 内片段宽度读取和余项计数宽度读取。该函数先取消片段隐藏，读取各片段尺寸，再逐步改写余项计数并读取宽度，最后隐藏放不下的片段。这条同步读写路径与诊断构建的布局耗时下降相互印证。

## 优化方向

1. 摘要测量按帧集中调度，分离写入与读取，复用稳定片段宽度，避免每个摘要各自反复显示、测量和隐藏。保留按真实可用宽度展示完整片段的行为。
2. 将复杂单元格纳入横向可视范围管理；屏外保留行高与列宽信息，活动编辑内容维持挂载，避免通过挂载整棵字段树获取几何尺寸。
3. 复杂预览按可见高度限制实际挂载的直接子项。选中展开和详情编辑按需要提供完整内容，减少被 CSS 裁剪但仍参与渲染与布局的节点。
4. 对虚拟行和复杂字段组件建立稳定的复用边界，随后复测剩余脚本成本；overscan 调整放在内容和测量成本下降后评估。

这些方向尚未作为正式功能实现。优化验收需保留字段顺序、引用显示、动态行高、编辑草稿、键盘导航、选中展开、列宽变化及摘要截断行为，并使用同一夹具串行前后对照。

## 复现

```powershell
node editors/cfd-editor/frontend/tests/browser/complex-performance.mjs
$env:COMPLEX_PERF_NO_SUMMARY_MEASURE = '1'
$env:COMPLEX_PERF_OUTPUT = "$env:TEMP/coflow-complex-performance-no-summary.json"

node editors/cfd-editor/frontend/tests/browser/complex-performance.mjs
Remove-Item Env:COMPLEX_PERF_NO_SUMMARY_MEASURE, Env:COMPLEX_PERF_OUTPUT, Env:COMPLEX_PERF_SCENARIOS
```

默认 JSON 与独立 CPU profile 写入系统临时目录 `coflow-complex-performance.json`、`coflow-complex-performance.cpuprofile`；诊断结果使用指定输出文件。性能采样完成后执行工程检查，避免构建负载干扰测量。
