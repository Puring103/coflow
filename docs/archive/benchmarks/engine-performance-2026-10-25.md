## 环境与测量口径

- 基线提交：7e9d4fdebabda2c440ed80d1b1f39651801f1387。
- Windows 11 10.0.26200；Intel Core i5-13600KF，14 核 / 20 逻辑处理器；约 32 GiB 内存。
- rustc 1.99.1 / cargo 1.99.1，Release 构建。基准串行运行，采样期间不执行编译或回归测试；没有启动或停止桌面编辑器。
- 操作系统调度和文件缓存保持默认。加载结果是预热后的新会话构建，不是清空磁盘缓存后的冷启动。混合核心调度、后台负载和分配器状态仍会带来波动，单机结果不代表所有硬件。
- 新工具为 [engine_perf.rs](../../../crates/coflow-runtime/examples/engine_perf.rs)，每项预热一次，保存全部原始样本；前次返回值在下次计时前释放。模型输入生成、临时项目生成不计时。工具的中位点取排序后 n/2 下标，偶数样本使用上中位点；P95 使用最近秩定义。
- 模型构建包含 build 内部输入与临时对象析构，不包含返回模型的析构。会话构建不包含返回会话析构；校验包含内部临时模型释放；修改包含旧代次释放、真实事务落盘、请求构造及结果断言，不包含返回报告析构。因此不能把不同入口的差值直接当作某个内部阶段耗时。
- 现有 check 基准为两次预热、七次采样；execution 交替测量全量与增量。它的执行时间包含 tasks.clone 和输出析构，不是纯表达式解释器时间。
- 进程峰值工作集包含夹具、缓存、候选代次和分配器保留内存，不等于模型独占内存，也不等于分配字节数。本轮未采集分配次数或 CPU 火焰图。

## 夹具与有效性

新的端到端夹具每条记录有 20 个字段，包含字符串、数字、数组、字典、嵌套对象、可选对象、两条引用及跨记录引用读取。每文件 1,000 条记录，记录身份全局唯一。每条记录有 4 个检查根，项目另有一个集合检查根。

- name 修改只影响本记录规则。
- value 修改会影响读取 parent.value 的记录；引用分布为环，每个目标实际只有一个 parent 读者，可用于观察保守跨记录失效的放大。
- rating 为无规则依赖字段，工具支持独立测量。
- grouped 按文件连续修改；interleaved 将相同数量的记录分散并交错到各文件。两者写入数量相同，但小批次触及文件数可能不同，不能将全部差值归于排序。
- 每次修改使用全局递增的新值，包含预热在内都是真实修改。断言无诊断、记录数正确、每个写入值正确；最终从磁盘独立重载，比较所有记录的目标字段，并检查无诊断。

历史编辑器基准需要保留单独解释：perf_smoke.rs 的 Item ID 未包含文件编号，多文件夹具产生重复身份。100×1,000 配置生成 110,000 条草稿，其中 10,000 Item 因重复被剔除，最终保留 100,000 Entity，且触发失败后重试。旧报告中的 30–36 秒加载不是健康工程基线，不能与本报告作直接优化前后对照。

## 基线结果

### 项目加载、源码校验与真实修改

表内为中位数，单位秒。1,000 条的连续修改采集 100 个样本，用于观察尾延迟；其余千条入口采集 7 次。10,000 条采集 5 次，100,000 条采集 3 次；后两者作为容量与中位数初筛，不据此声称 P95。

| 入口 | 1,000 条 / 1 文件 | 10,000 条 / 10 文件 | 100,000 条 / 100 文件 |
| --- | ---: | ---: | ---: |
| 新会话数据构建，含全部 check | 0.132 | 2.562 | 25.544 |
| 完全相同源码重复校验 | 0.131 | 2.140 | 23.998 |
| 一个 name 字段变化的草稿校验 | 0.135 | 2.152 | 20.051 |
| 一个 name 字段真实提交 | 0.236 | 1.554 | 19.594 |
| 同文件 1,000 个 name 修改 | 未测 | 22.836 | 45.125 |
| 跨文件交错 1,000 个 name 修改 | 未测 | 42.648 | 83.609 |

十万条局部校验三次为 20.051 / 17.579 / 25.205 秒，局部提交三次为 19.946 / 14.861 / 19.594 秒。样本不足以对尾延迟或相同文本与变更文本的性能差异作稳定判断。项目配置打开及 schema 编译均低于 1 ms，与数据阶段相差多个数量级。

千条连续提交的 P95 为 259.54 ms，100 次总计 37.45 秒，闭环吞吐约 2.67 次/秒。其中一次耗时 13.96 秒，其余样本约 202–274 ms；异常样本原样保留，尚未归因，不能归为纯引擎 CPU 耗时，也不能在用户延迟统计中删除。

计数器确认局部 name 提交仅重载一个文件、执行 4 个检查根，但 records_materialized 仍等于项目全部记录，records_reused 为 0，ref_edges_rebuilt 等于全部两条/记录引用。十万条时即重建 100,000 条记录和 200,000 条边。同文件千次修改执行 4,000 个检查根，但模型重建规模仍为全部十万条。

跨文件千次修改在十万条工程中触及 100 个文件，三次样本为 74.223 / 83.609 / 86.301 秒。该场景同样执行 4,000 个检查根。相对于同文件提交，它还包含更多文件事务及被修改源的解析成本；当前按操作重复解析进一步放大这些成本。

稀疏引用对照中，万条工程单个 value 修改约 2.036 秒，却执行 40,000 个检查根。环形引用下，直接变化记录和唯一 parent 读者共两条记录，按整规则语义只需要 8 个根；当前静态规划仍扩大到同类型全部记录。这个任务数量差异直接支持精确反向依赖的方向，不能用它推导整次提交会同比加速，因为全量模型重建仍存在。

完整流程的进程峰值工作集：千条约 105.7 MiB，万条 name 场景约 907.4 MiB，十万条约 8.60 GiB。十万条运行含多次新会话、草稿校验、修改以及最终独立重载。该数值不是最终模型常驻内存；优先分析同时存在的缓存草稿、汇总草稿、builder 中间值与新旧模型，以及递归对象容器和来源元数据。

维度夹具有 8 个字段，含跨记录插值，投影后逐记录验证直接值和传播值。1% 覆盖在变体数由 1 增至 10 时，构建增长约 4.6 倍；现有实现仍对所有记录重算各变体，稀疏覆盖没有相应减少扫描范围。已投影视图的相同选择已有快路径；从基础模型再次选择同一变体仍需重建，当前没有历史选择结果缓存。

错误文本长度约增长 10 倍而耗时增长约 106 倍，与每次恢复重新 tokenize 整个文件的代码路径一致。这是高频编辑无效中间文本需要优先处理的问题，不能只测合法输入。

当前 64 位布局实测：CfdValue 56 字节、LoadedValueDraft 56 字节、CFD AST Value 96 字节、CfdRecord 168 字节、CfdObject 48 字节、CfdDataModel 72 字节。以上均不包含堆数据。快照 clone 已共享 Arc；主要复制成本在模型构建中间表示和更新路径。

## 安全增量检查的合同

当前已有静态依赖规划，局部规则、内联 data 规则、记录集合和维度均有失效逻辑。增量最小单位是整个规则实例（命名或匿名）；不能将减少重复规划误做成仅执行一个断言。此前预算中断或变体目录改变时会重新全量检查。

精确增量进一步需要：

1. schema、规则、源版本与模型代次一致；稳定身份不能直接复用上一代 Vec 下标。
2. 直接字段变化和模板/默认值/维度传播形成有效变化闭包；记录新增、删除、重命名、类型变化及错误记录重新被接纳都参与。
3. 记录规则实际读取的字段、引用解析、集合成员、对象结构、覆盖存在性和控制条件；引用改向时同时处理旧/新依赖。
4. 源诊断、模型诊断、check 诊断按来源与规则实例缓存；未变化错误文件诊断和失效后的旧内联路径均正确处理。
5. 原子文件事务、外部编辑冲突检查、旧 revision 拒绝和发布一致性继续成立。
6. 增量与全量均完成时，规范化业务结果与诊断相同；预算中断单独验证恢复。

当前请求预算只计算本次执行任务，缓存任务不计费。因此**同一有限预算下，全量与增量的预算诊断和执行截止位置不保证相同**。若要求模拟全量预算，需要保存逻辑成本、重算全量顺序的预算前缀并可能重新执行被截断任务，这是语义选择，实施前确认。

示例：两条记录各检查长度为 4 的 nums.isUnique，每任务工作为 4+1，请求预算 10，旧全量完成。将第一条数组改为 6 项，增量耗 7 完成，新全量却会在第二条超限。这一例子由执行器计费路径推导，本轮未单独运行该反例。

通用全局量词、全扇出引用与 schema/config 变化允许触发大范围或全量工作；不能承诺所有修改都 O(1)。any 的后续元素求值错误目前仍有语义意义，不能未经确认改成短路；并行 check 也需要先解决预算与诊断顺序。

## 建议优化目标

以下为待确认的验收目标，不是本轮已经达到的性能，也不是已由优化原型证明的收益。主夹具固定为 100,000 条、100 文件、每条 20 字段和 4 个检查根，含上述嵌套与引用。局部交互目标要求实际依赖闭包较小；全表规则和全扇出修改单独验收。阶段目标依据当前整文件重解析、全量物化和重复规划的可消除工作提出；每阶段先以同夹具复测确认收益，再推进下一阶段。

| 指标 | P0：消除重复工作后的阶段目标 | 完成存储共享与增量架构后的目标 |
| --- | --- | --- |
| 十万条新会话数据构建，含 check | 中位数比本基线下降至少 30% | 中位数 ≤5 秒 |
| 十万条单字段真实提交，本地规则 | 中位数下降至少 30%；此阶段仍可能是秒级 | P50 ≤50 ms，P95 ≤100 ms |
| 十万条一文件草稿局部修改校验 | 中位数下降至少 30% | P95 ≤100 ms；相同源版本重复请求 ≤10 ms |
| 万条工程、同文件 1,000 次字段修改 | 中位数 ≤5 秒，整文件解析次数与操作数无关 | 随十万条批量目标一并验收 |
| 十万条、同文件 1,000 次修改 | 耗时接近该规模一次重建加批量补丁，避免 B 次解析 | P50 ≤500 ms，P95 ≤1 秒 |
| 十万条、跨 100 文件 1,000 次修改 | 先验证解析/源码生成次数按文件数增长 | P50 ≤1.5 秒，P95 ≤3 秒 |
| 20,000 Item、18 根规则的全量规划 | 现有相同夹具中位数至少加速 4 倍 | 规划随唯一任务数增长，消除 R² 插入尝试 |
| 同上完整 check 求值 | 中位数至少加速 1.5 倍 | 中位数至少加速 2 倍；错误和预算结果按合同验收 |
| 1,000 条错误文本解析 | 中位数 ≤30 ms | 文件长度与错误数增长不再产生乘积级重扫描 |
| 十万条完整流程峰值工作集 | 相同测量流程至少下降 20% | 至少下降 50%；释放旧代次后持续操作不线性累积 |

局部高频验收建议以 **10 次真实修改/秒，持续 1,000 次操作**进行开放到达率测试，包含排队时间；P95 达标且队列不持续增长。另跑闭环连续提交测最大吞吐。新旧版本在同机交替运行至少三轮，各轮至少 100 个局部修改样本；保留异常停顿，不用剔除异常后的数字替代真实尾延迟。

工作量目标与时间目标共同成立：

- 单一局部字段修改，只有变化记录及实际依赖闭包重新物化；无关记录复用。现有“重建所有记录但少跑 check”不算实现增量模型。
- 独立批量修改按文件固定次数解析，B 倍操作不引入 B 倍完整文本复制。
- 稀疏引用更新只重查实际读者的整条规则；100,000 条同类型不意味着 100,000 个读者。
- 成功断言不生成展示诊断字符串；规则规划对每个目标只展开一次相同规则。
- 保持固定记录数，维度变体、字段宽度、集合长度翻倍的增长曲线与优化后的算法阶数相符。

默认检查任务上限为 1,000,000。十万条、每条 18 个根会超过该上限，不能把预算拒绝当作高性能完成，也不能为了跑分静默提高上限。扩展高密度规则容量需要单独确认资源预算目标。

## 测量缺口与后续验收

本轮覆盖核心分层入口，但没有把完整加载拆到每个内部阶段，也没有测 GUI、IPC、图布局、C# runtime 或 LSP 输入到诊断展示的端到端延迟。需要补充的长期矩阵包括：

- 100 次以上连续操作的十万条项目；记录 P50/P95、吞吐与内存是否稳定。
- 固定总记录量改变文件数 10/100/1,000；宽字段、深对象、大字典、深层默认值。
- 插值链、公共源高扇入、引用删除/改向、稀疏/密集维度及变体目录变动。
- 0% / 1% / 100% 失败检查，错误恢复与预算恢复，随机连续修改及撤销。
- 内部计数：真实解析次数/字节、分配次数/字节、验证/物化节点、引用边重建、依赖访问、诊断渲染；现有 work counters 不能完整表示失败重试次数。

优化验收同时比较性能与全量 oracle。普通开发门禁仍只有 cargo check --workspace 与 cargo test --workspace；基准是专项性能证据，不加入新的普通提交或补丁发布门禁。

## 复现

先完成构建，再串行测量，避免编译负载污染样本：

```powershell
cargo build --release -p coflow-runtime --example engine_perf
cargo bench -p coflow-runtime --features internal-check-bench --bench check_planning --bench check_execution --bench check_limits --no-run
$env:ENGINE_MODE = 'model'
$env:ENGINE_RECORDS = '2000'
$env:ENGINE_SAMPLES = '7'
& target/release/examples/engine_perf.exe

$env:ENGINE_MODE = 'pipeline'
$env:ENGINE_RECORDS = '100000'
$env:ENGINE_FILES = '100'
$env:ENGINE_SAMPLES = '3'
$env:ENGINE_UPDATE_SAMPLES = '3'
$env:ENGINE_BATCHES = '1,1000'
$env:ENGINE_FIELD = 'name'
& target/release/examples/engine_perf.exe
```

check 的三个可执行文件由 bench --no-run 输出其实际路径，依次直接执行。完整端到端矩阵：

| 名称 | records | files | samples | update_samples | batches | field |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| pipeline-1k-name | 1,000 | 1 | 7 | 100 | 1 | name |
| pipeline-10k-name | 10,000 | 10 | 5 | 5 | 1,10,100,1000 | name |
| pipeline-100k-name | 100,000 | 100 | 3 | 3 | 1,1000 | name |
| pipeline-10k-value | 10,000 | 10 | 3 | 3 | 1 | value |

samples 控制加载与草稿校验，update_samples 控制每个批量场景的连续真实修改；各项另有一次预热。ENGINE_DIMENSION_RECORDS 默认为 1,000，ENGINE_BROKEN_RECORDS_MAX 默认为 1,000；后者防止当前平方级错误恢复令默认基准过长。每次 pipeline 自动创建并清理独立临时目录，不接受用户工程路径。
