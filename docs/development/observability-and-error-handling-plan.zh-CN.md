## 实施状态

本次已接通本机 JSONL 日志、操作与错误编号、运行日志健康计数、前端问题历史、日志目录入口、可编辑诊断预览和手动文件导出。`coflow-observability` 负责宿主日志；引擎和 staging 只发出受控事件。桌面命令的操作 span 显式进入阻塞线程。CLI 使用 `COFLOW_LOG=1` 开启文件日志，保持标准输出协议不变。

已修复 E01—E05、E07 的主要调用链，以及 E08 中 build/dist/target 祖先导致的漏监听。源码已提交但刷新失败时保留更新草稿并提供只重载的恢复按钮；多文件发布结果保留恢复失败和备份位置；不完整恢复阻止继续编辑。新建节点并连线，以及纯数据批量历史回放走单次引擎事务。含布局设置等独立副作用的历史仍逐项执行，部分失败时准确拆分历史，不重复执行已完成部分。

源码发布沿用协作式磁盘基线校验，不承诺对任意外部程序的原子 CAS，也不承诺进程被强制终止时的跨文件事务恢复。

日志按应用共享文件锁轮转，每个应用最多 5 个 10 MiB JSONL 文件，下一次写入时清理超过 7 天的日志。异步队列最多 512 条，满时丢弃并计数；另保留一个最后 panic 元数据文件。诊断包默认包含最近最多 1 MiB 的日志和错误编号；错误文本、堆栈由用户勾选后才进入预览。用户可以编辑预览再保存，应用不自动上传。

验证覆盖源码已提交刷新失败、创建失败传播、重命名历史推进、非数据批量部分执行、引擎复合操作失败不落盘、外部源码冲突、恢复失败备份保留、监听过滤、日志容量与写入故障。普通开发门禁保持不变。

发布前另需在实际安装环境验收：Windows/macOS 原生启动失败与崩溃、升级安装期间的未保存编辑、多实例竞争和磁盘满压力、生产 sourcemap/原生符号归档及还原。当前已生成隐藏 sourcemap，尚未把符号归档接入发布流水线；不能将本次测试通过等同于发布验收通过。以下章节保留审查依据和完整目标，未由上述实施状态确认的扩展指标、宿主适配和发布验收仍按计划推进。


## 1. 目标与结论

公开使用前，Coflow 需要让用户与维护者能够回答四个问题：发生了什么、数据是否已经保存、如何恢复、如何提供足够的排查证据。

当前语言与数据诊断已有错误码、位置、上下文及部分修复建议；CLI 自动化协议还有冲突和恢复结果。主要缺口集中在运行日志、编辑器操作结果传递和错误呈现。实施重点是保留真实结果，再让日志与界面共同消费这一结果。

本计划覆盖桌面启动、前端与 IPC、项目会话、引擎加载与校验、数据与源码写入、发布与恢复、历史、文件监听、设置、插件、图布局、更新、CLI、独立和内嵌 LSP，并核对 C# Loader 的宿主边界。现有 README、网站翻译等并行改动不属于本次变更。

验收目标：

1. 每个关键操作都有可关联的开始、结束、耗时和结果；失败可追溯到阶段与原因。
2. 界面准确区分未写入、已保存、已恢复、部分恢复失败和状态未知。
3. 可预期的数据错误定位到诊断；程序异常保留堆栈和运行环境。
4. 日志落在用户本机目录，有容量和保留期限，可在项目未打开时查看与导出。
5. 高频操作不会刷满日志，日志故障不会引发递归报错或无界资源占用。
6. 默认日志不包含源码、字段值、完整 IPC 参数和凭据；导出内容可预览。

## 2. 审查证据与验证范围

证据分为三类：

- **已复现**：直接执行现有 TypeScript 控制器，用模拟 I/O 注入故障，检查状态与返回结果；没有启动桌面编辑器。
- **代码确认**：调用链中存在明确的信息丢失、状态缺失或无日志分支。
- **待专项验证**：涉及真实安装器、跨进程竞争、原生崩溃等环境，需要在实施阶段加入受控验证。

本会话前一轮已通过 `cargo check --workspace` 和 `cargo test --workspace`。本轮新增验证是四项控制器故障复现，没有重复运行未变更的 Rust 全工作区检查。没有执行实际升级、原生崩溃或跨平台 GUI 测试。已有测试通过不代表这些边界已有覆盖。

| 复现 | 注入条件 | 当前实际结果 | 目标结果 |
| --- | --- | --- | --- |
| 源码保存后刷新失败 | `write()` 先写入新文本，再抛出 `kind: committed` | 磁盘为新文本，`base` 仍为旧文本，`dirty=true`，`conflict` 等于刚保存的文本，`saved()` 未执行 | 确认已提交的文本，保留更晚草稿，进入会话恢复状态 |
| 新建记录失败 | 后端 `insertRecord()` 抛出权限错误 | 上层 Promise 正常完成，调用方继续执行成功路径；历史为空 | 返回明确失败，上层保留创建草稿 |
| 重命名撤销 | 撤销过程中调用 `history.rebind()` 后返回 committed | `undo=1`、`redo=0` | 成功撤销后 `undo=0`、`redo=1` |
| 批量撤销中断 | 第一条撤销提交，第二条返回 failed | 已执行第一条，整批返回 failed，未补偿前面的提交 | 引擎原子执行，或返回准确的部分执行结果并进入恢复流程 |

### 3.3 需要专项验证的风险

- 更新流程直接 `downloadAndInstall()` 再 `relaunch()`，没有接入源码草稿、结构化编辑和待提交写入的统一检查。需用安装器替身验证；不能仅凭普通窗口关闭拦截推断升级一定安全。保存与冲突未解决时，更新应停在安装前。
- watcher 将目录事件与文件事件区别处理；目录移动、外部输入根创建、监听失效及持续事件流下的重载行为，需要真实文件事件用例验证。当前不把所有平台的目录事件行为判定为同一种缺陷。
- panic、进程强制终止、断电、WebView 原生崩溃具有不同保证。Rust panic hook 不能捕获所有原生崩溃，正常退出 flush 也不能保证强制终止前的队列全部写盘。
- 共享 staging 的检查与文件替换并非 OS 提供的跨进程原子 compare-and-swap。需要受控竞争测试，并明确数据保护边界。

## 4. 应保留的基础与模块边界

1. `coflow-language`、`coflow-model`、`coflow-checker` 继续生成语言/数据/规则诊断，不自行创建日志文件。现有预算、诊断定位、引用和增量校验结果保持为事实来源。
2. `coflow-runtime` 负责项目操作、阶段、性能计数和发布结果。源码、结构化写入、项目结构变更、代码生成使用一致的发布与恢复契约。
3. `coflow-staging` 负责文件系统发布和可观测的恢复、清理结果；不依赖编辑器或安装全局 logger。
4. 编辑器 core 负责会话、代次和宿主无关的操作结果；Tauri 负责日志目录、文件写入、原生异常与打开/导出入口。
5. 前端负责草稿、交互状态、错误呈现和前端异常采集；不通过解析错误字符串推断是否保存成功。
6. CLI 与独立 LSP 的日志配置由 CLI 宿主安装；内嵌 LSP 使用编辑器已配置的日志环境，避免重复安装全局 subscriber。
7. C# Loader 已有 `LoadResult.Diagnostics` 和 `CfdLoadException.Diagnostics`。它是用户应用中的库，日志由调用方选择；本轮补充诊断接入示例，不让 Loader 自动写用户磁盘或上传信息。

## 5. 日志方案

### 5.1 技术组织建议

建议采用 Rust `tracing` 事件/span，加一个由宿主初始化的结构化文件写入器。编辑器 core、runtime、LSP 只发事件；底层逐字段求值不增加常态日志。库代码不调用全局初始化。

CLI 与桌面共享的格式、脱敏、轮转和导出选择规则，建议放入一个小型宿主支持 crate（暂名 `coflow-observability`）。它不拥有项目模型或 UI 错误语义；只有宿主依赖日志写入与 subscriber 部分。是否新增此 crate 是实施前的架构确认项。

前端在 `invokeCommand`、错误归一化、全局异常捕获和插件边界采集，通过专用的有界批量 IPC 交给宿主。日志 IPC 本身绕开普通命令日志包装，防止失败时递归调用自己。前端上报限制字段、长度、批大小和速率，宿主再次验证。

普通 `tracing-appender` 配置不能直接视为已满足全部容量与保留要求；实现需要验证大小、数量、总量和多进程并存下的实际行为。

### 5.2 事件字段与关联

| 字段 | 作用 |
| --- | --- |
| `timestamp`、`level`、`event`、`component` | UTC 时间、级别、稳定事件名、模块；界面按用户时区展示 |
| `build_id`、`version`、`platform`、`arch`、`pid`、`run_id` | 定位发布构建及一次进程启动；详细环境只在启动/导出元数据记录 |
| `request_id`、`operation_id`、`parent_operation_id` | 关联一次 IPC、用户操作与复合子操作 |
| `session_id`、`revision_before`、`revision_after` | 定位会话与模型代次；session_id 不能脱离 run_id 单独作为全局身份 |
| `phase`、`duration_ms`、`queue_ms` | 区分排队、执行、发布、恢复和 UI 刷新 |
| `outcome`、`persistence`、`refresh_state` | 分别描述操作结果、磁盘结果、界面/会话刷新结果 |
| `error_id`、`code`、`cause_code`、`os_error` | 关联某次错误与稳定错误类型，保留系统错误种类 |
| `file_count`、`record_count`、`diagnostic_counts`、`retry_count` | 复用已计算的小型统计，不为日志额外扫描模型 |
| `plugin_id`、`plugin_version`、`worker_request_id` | 对应模块的限定上下文 |

`error_id` 标识一次失败；诊断 `id` 标识诊断，二者分别维护。前端 request_id 与宿主 operation_id 明确映射。异步任务、`spawn_blocking` 和 watcher 线程显式携带上下文，不假设线程局部 span 自动跨线程传播。

一次编辑的事件序列应能连接：用户提交 → IPC → 候选验证 → 发布 → 后端代次 → 前端刷新 → 历史推进。单个错误在拥有者边界记录一次主错误，其余层补充关联阶段，避免相同异常重复记录多份。

### 5.3 级别与噪声控制

| 级别 | 建议用途 |
| --- | --- |
| ERROR | 操作异常失败、恢复失败、panic、未处理异常、后台工作线程异常退出 |
| WARN | 外部写冲突、监听/校验功能降级、备份清理失败、日志写入故障、持续超时 |
| INFO | 启动/退出、项目打开/关闭、构建结果、写入终态、更新阶段、插件生命周期 |
| DEBUG | 操作阶段、代次丢弃理由、缓存/增量选择、监听过滤与耗时明细 |
| TRACE | 短期定向排查，仍受内容白名单与限流约束 |

正常语法错误、必填项缺失和规则未通过属于诊断，不逐条写成程序 ERROR。后台取消、过时代次、动画取消和已关闭会话的正常清理通常为 DEBUG 或不记录。真实故障即使因会话切换不再弹到当前 UI，也保留关联日志。

重复 watcher 错误、插件回调错误和网络检查失败按错误类型与上下文聚合，保留首次、最近一次、次数和时间窗口。高频补全、hover、拖动、行高与输入去抖只保留摘要或慢操作；用户发起的实际写入仍保留精简终态。队列满时记录丢弃计数并优先保留错误，不能无声丢失。

### 5.4 存储、导出与日志自身故障

以下是建议初值，实施前确认：默认 INFO；单文件 10 MiB；最多 5 个轮转文件；最长保留 7 天，容量与时间先达到者触发清理。保留额度应按应用日志目录总量控制，而不是每次启动无限新增 5 个文件。

- 桌面使用系统用户级应用日志目录，由宿主路径 API 解析；不写项目目录，避免 watcher、自身重载和 Git 污染。界面直接显示实际路径。
- 多进程使用独立 run_id 文件或明确的锁协议；清理跳过活动日志，避免一个实例删除另一个实例正在写的文件。
- 主日志采用 JSON Lines；按 component/level 过滤即可查看前端、引擎与错误日志。若提供独立错误文件，应作为同一事件流的派生视图，不维护第二套事件语义。
- 设置有界后台队列、单事件字节上限、批大小上限；写入不得长时间持有会话锁。ERROR 采用有界的优先刷新策略，退出时设置 flush 时间上限。
- 日志目录不可写、磁盘已满或轮转失败时，显示一次“日志记录不可用”，保留有界内存错误摘要；可用时同时输出 stderr。不能无限重试或用失效日志通道报告自身错误。
- panic hook 在宿主尽早安装，记录线程、位置和尽可能可用的堆栈；避免依赖可能已被占用的会话锁。后台任务 panic 要同时反馈任务失败，不能记录后继续假设会话安全。
- 记录正常退出标记；上次启动缺少标记只能说明“上次未正常结束”，不能直接宣称“发生崩溃”或“数据已损坏”。

日志是排查证据，不代替持久事务日志。多文件替换在进程终止时的恢复保证需要独立的文件系统契约；不得根据最后一条日志猜测已经全部提交或恢复。

### 5.5 信息范围

默认只记录操作类别、计数、代次、状态、稳定代码与脱敏后的原因。项目路径采用本次运行内的项目别名；文件定位优先使用项目相对路径，导出允许用户检查和隐藏文件名。真实备份位置在本机恢复界面可见，导出时另行处理。

禁止直接使用 `Debug` 或 `#[instrument]` 默认参数捕获整个 request、源码、字段值、模型、配置、插件脚本和 HTTP 请求。使用显式字段和 `skip`。

错误 message、check 上下文、panic payload、JS 堆栈和 URL 也可能含有用户文本或绝对路径，须在事件构造处分类处理，并在导出时再检查。排除 IPC 参数不等于已经完成脱敏。调试模式也不默认开放原始项目数据记录。

### 5.6 诊断包

编辑器提供“打开日志目录”“复制错误详情”“导出诊断包”，在欢迎页、错误详情和主界面均有可达入口。

建议诊断包包含：构建/系统/WebView 版本、选定时间段的日志、问题列表、启用插件的 ID 与版本、日志丢弃计数与写入健康状态，以及失败操作的脱敏恢复摘要。支持包含上次未正常结束的运行，导出读取稳定快照并限制总大小。

默认不包含 CFD/CFT、完整配置、数据值、备份文件或完整项目压缩包。导出前展示文件清单与信息范围，用户选择目标位置；不自动上传。日志不可写时，仍能复制内存中的有限错误摘要并明确标注证据不完整。

## 6. 错误契约与界面

### 6.1 统一结果

建议把“操作是否成功”“是否落盘”“是否刷新完成”作为独立维度，例如：

- `outcome`：succeeded / rejected / failed / cancelled / superseded。
- `persistence`：not_attempted / unchanged / committed / restored / partial / unknown。
- `refresh_state`：not_required / current / pending / failed。

以上为设计词汇，最终字段名在接口实施前确认。`superseded` 只说明结果不再适用于当前视图，不能自动推出“没有落盘”。重试动作由持久化结果决定，不能仅依赖 failed。

runtime 提供阶段与发布回执；core 包装宿主无关错误信息；前端统一生成标题、解释与动作。不要把 operation_id、中文 UI 文案和按钮枚举塞进语言诊断 crate。

编辑器错误至少携带：稳定 code、error_id、operation_id、操作类型、失败阶段、用户消息参数、底层原因类别、原诊断集合、持久化/刷新状态、受影响文件和可用恢复信息。完整原因链进入受控日志，界面提供脱敏后的可展开详情。

恢复报告包含实际尝试发布的文件、已成功发布文件、已恢复文件、恢复失败文件和保留备份位置。原始失败与恢复失败分别记录，后者不得覆盖前者。未知状态明确标为 unknown。

### 6.2 提示与动作矩阵

| 情况 | 界面信息 | 主要动作 |
| --- | --- | --- |
| 用户数据不合法 | 指明文件/记录/字段和诊断；说明本次操作是否被拒绝 | 跳转问题、保留草稿 |
| 外部修改冲突 | 文件已被其他操作修改；本次写入未提交 | 比较、重新读取；用户明确选择后才覆盖 |
| 权限不足/占用/空间不足 | 指明受影响文件及原因；说明本次修改未保存 | 处理系统问题后重试，复制详情 |
| 已保存、刷新失败 | 修改已保存，当前视图未更新 | 恢复会话/重新加载，不重复提交 |
| 发布失败且恢复完成 | 本次操作失败，已恢复原文件 | 查看详情，处理原因后重试 |
| 恢复未完成/状态未知 | 列出待核实文件和备份；说明停止继续写入 | 查看恢复信息、导出日志、重新核对后恢复 |
| 后台校验失败 | 检查暂不可用；现有诊断可能过期 | 重试检查、查看详情 |
| watcher 失败 | 自动刷新不可用，当前视图可能过期 | 手动刷新、恢复监听 |
| 插件失败 | 指明插件和失败功能；说明其他功能是否可用 | 禁用该插件/贡献点、查看详情 |
| 更新失败 | 区分检查、下载、校验、安装和重启阶段 | 与阶段匹配的重试或手动重启 |
| 前端渲染异常 | 界面发生异常；对未保存内容只作有依据的说明 | 复制详情、导出日志、受控恢复 |

重载、关闭、更新和恢复都需要遵守同一个未保存草稿与待提交操作协调器。不能因错误边界提供“重新加载”就绕开保存检查，也不能在未知磁盘状态下让用户盲目点击“重试保存”。

### 6.3 前端呈现

- 将单个字符串 banner 收敛为结构化 issue store：当前阻塞问题持续显示，非阻塞问题可关闭但进入有界历史。
- 局部输入校验留在字段旁；操作失败留在发起操作的位置；全局故障使用统一区域。多处展示同一 error_id，不重复创建事件。
- 创建或编辑失败保留草稿、选区与当前弹窗；成功后才关闭。
- 失败候选的诊断与当前已发布代次的诊断分开展示，避免把未提交的数据错误混入当前项目状态。
- 标题采用用户术语，详情保留代码与技术原因。支持中文文案，错误分类和动作不依赖中英文字符串匹配。
- React 错误边界、全局同步错误、未处理 Promise、worker 与插件生命周期分别接入；跨层去重。

## 7. 分模块日志覆盖清单

| 模块 | 应记录的关键节点 | 需避免的开销/误报 |
| --- | --- | --- |
| 启动与退出 | logger 初始化、版本、宿主初始化、窗口/WebView、正常退出/异常终止线索 | 不将缺少退出标记直接判定为崩溃 |
| IPC | 命令名、请求关联、排队、完成、反序列化/转换失败、任务失败 | 不记录 args/result 全量；日志命令免于自身包装 |
| 项目会话 | 打开、重载原因、配置/编译/模型/规则阶段、代次接纳/丢弃、关闭 | 高频重载合并，统计复用已有计数 |
| 引擎校验 | 完成/未完成、诊断分布、预算耗尽、增量或全量路径、耗时 | 不逐记录记录常规校验，不重复记录全部诊断消息 |
| 写入与构建 | 准备、验证、发布、恢复、清理、结果、备份定位 | 不记录源文本和生成代码正文 |
| 历史与草稿 | 提交、撤销/重做、批次、冲突、恢复阻塞 | 不记录每个按键或字段原值/新值 |
| watcher | 注册根、合并事件数、过滤理由、外部变化判断、重载及发送结果 | 正常内部写入和关闭通道不作为 ERROR |
| 设置 | 共享/本机作用域、写入结果、版本不支持、存储不可用 | 列宽/行高/标签切换聚合；分别表明部分成功 |
| 插件 | 安装、加载、激活、回调、挂载、禁用、卸载、失败贡献点 | 同类错误限频；不收集插件源文件 |
| 图布局 | 请求编号、节点/边数量、执行耗时、超时、worker 终止 | 不记录整个图或坐标数组 |
| 更新 | 当前/目标版本、各阶段、网络/签名/权限错误、待保存检查 | 不记录凭据、带查询参数的敏感 URL |
| CLI | 命令阶段、耗时、退出状态、事务摘要 | stdout 保持既有 JSON/文本/format/LSP 协议 |
| LSP/扩展 | 会话、请求类型和耗时、版本丢弃、校验 worker 状态、协议错误 | 不记录文档内容；扩展提供可见输出通道 |
| C# Loader | 宿主消费诊断、异常与耗时的接入示例 | 库不配置全局 logger，不默认写文件 |

## 8. 实施阶段与交付物

### P0：固定结果契约与回归样例

交付：操作/持久化/刷新状态表、错误分类、现有调用链清单，以及 E01—E08 的最小用例。

- 明确真实提交和恢复结果在 staging → runtime → core → frontend 中的归属与传递。
- 先建立失败、已提交未刷新、部分恢复失败、superseded 的受控故障注入。
- 确认第 10 节中的产品与架构参数；只在确认后落实具体接口与存储策略。

完成标准：每一种失败均有明确状态和动作，无需前端猜测 message 的含义。

### P1：修正写入与历史结果传递

依赖 P0。交付：统一的发布回执和编辑器操作结果，以及对应回归用例。

- CFD 写入与代码生成复用共享发布/恢复编排；源码保存及项目结构变更接入相同结果契约。
- 公开 mutation 方法返回明确结果，创建窗口、图谱复合操作和插件正确消费。
- 修复已保存后刷新失败、重命名撤销和批量部分提交问题。
- 部分恢复失败/未知状态进入阻塞恢复状态；保留备份信息与原始错误。
- 修复 watcher 目录过滤，并验证外部输入与目录事件边界。

完成标准：磁盘状态、后端代次、前端状态和历史一致；出现不一致时能准确报告并停止危险重试。

### P2：建立日志基础设施

格式依赖 P0，接入 P1 的权威结果。交付：共享宿主日志能力、桌面初始化、IPC 关联和前端异常采集。

- Rust 事件格式、日志写入、轮转、保留期限、限流、脱敏、健康状态和多实例隔离。
- 桌面启动早期初始化及 panic 捕获；后台线程上下文显式传播。
- 前端统一错误归一化、ErrorBoundary、全局异常和有界日志 IPC。
- 先覆盖项目打开、字段写入、源码保存、构建、刷新五条主链，再扩展其他模块。

完成标准：一次失败能从 UI error_id 定位到完整操作阶段；磁盘满和日志通道失败不会造成递归故障。

### P3：统一错误界面与后台健康状态

依赖 P1、P2。交付：issue store、错误详情/复制、恢复动作，以及局部编辑状态改造。

- 用统一 presenter 替换散落的字符串前缀、临时 banner 与不准确的“重试保存”。
- 恢复失败阻塞、草稿保留、候选诊断隔离、校验不可用和构建状态未知有明确表现。
- watcher、插件、worker、设置与更新按阶段记录；更新在安装前通过统一保存协调器。
- 正常取消和过时代次不弹错误；真实故障仍可在问题历史/日志查看。

完成标准：第 6.2 节所有状态有可理解的说明和可执行动作，操作失败不关闭未完成草稿。

### P4：形成可交付的排查能力

依赖 P2、P3。交付：日志目录入口、诊断包、CLI/LSP 日志接入、发布符号归档与用户说明。

- 欢迎页和故障界面均可复制/导出，支持当前运行与上次异常结束的运行。
- CLI 提供明确的日志启用方式（建议 `--log-level`、`--log-file`，最终命名待确认）；不污染 stdout。
- VS Code 输出通道显示 LSP 生命周期和 stderr；内嵌 LSP 不重复初始化日志。
- 发布构建绑定 commit/build_id，归档对应 source maps 与符号；用一个生产构建堆栈验证能还原到源码。
- 内部日志/错误契约放入 docs；公开网站仅说明日志位置、导出、错误状态和反馈方法。用户可用能力变化时更新对应技能任务指引，保持命令与诊断语义一致。

完成标准：维护者仅凭用户导出的脱敏诊断包，能定位至少一次前端异常、一次后端写入失败和一次已保存刷新失败。

### P5：公开宣传前验收

依赖 P1—P4。交付：覆盖矩阵、受控故障结果和遗留风险清单。

- 按第 9 节执行专项故障回归和性能对比。
- 核对所有 P1 及主链错误呈现问题；未完成项明确影响和发布判断，不用“已有日志”代替修复。
- 普通开发门禁仍仅为根目录 `cargo check --workspace`、`cargo test --workspace`。前端、IPC、日志和安装器替身用例是本专项验证，不新增为所有普通提交/补丁发布的强制门禁。
- 若随后发布 `X.Y.0`，执行 AGENTS.md 完整门禁；其他版本遵守对应发布规则。本计划本身不启动打包、安装或发布。

推进顺序为 P0 → P1 → P2 → P3 → P4 → P5。P2 的写入器可在 P0 确定后独立开发，但接入必须使用 P1 的真实结果。

## 9. 测试与验收矩阵

| 场景 | 关键断言 |
| --- | --- |
| 新建/批量写入/插件 mutation 被拒绝 | 返回明确失败、草稿保留、没有成功提示或后续连线 |
| 源码已保存、后端重载失败 | 不误报外部冲突，不重复落盘；新输入保留；恢复状态可见 |
| 新建/删除/添加来源已完成、重载失败 | 已提交信息完整；后续写入受控；恢复只重载 |
| 多文件发布第二项失败 | 报告第一项曾发布、是否已恢复；结果与实际文件逐项一致 |
| 恢复时遇到外部新内容 | 不覆盖外部内容；保留备份路径；显示部分恢复失败 |
| 清理备份失败 | 数据提交仍为成功，另外记录清理警告；不误导用户重做 |
| 源码验证期间外部修改 | 保留冲突双方，符合明确的跨进程写入契约 |
| 重命名 undo/redo、复合操作中途失败 | 历史与磁盘状态一致；失败后不重复执行已提交部分 |
| watcher 注册失败、根变化、目录移动、同名忽略目录 | 监听状态明确；该刷新的项目能刷新；过滤理由可查 |
| 事件发送失败、旧会话响应晚到 | 原故障有日志；旧 UI 不被污染；正常淘汰不是 ERROR |
| 校验/构建状态查询失败 | 显示未知/不可用，不能呈现为校验通过或无需构建 |
| 前端渲染/异步/worker/插件错误 | 各边界能捕获，堆栈和上下文可关联，重复错误有界 |
| 后台命令 panic、启动失败、非正常退出 | 留下可用证据，任务或会话失效明确；不承诺捕获所有 OS 崩溃 |
| 更新检查/签名/安装/重启失败 | 阶段与动作正确；安装前确认草稿与队列；使用替身，不操作用户编辑器 |
| 日志目录不可写/空间不足/轮转失败/队列溢出 | 有一次性提示与丢弃计数；无递归报错、无限重试或无界内存 |
| 多实例与保留清理 | 日志不混写，不删除活动文件，总大小和期限满足约束 |
| 脱敏 | 在源文本、字段值、异常消息、URL、路径注入哨兵，默认日志/导出不泄露受保护内容 |
| CLI JSON、format stdout、LSP Content-Length | 开日志前后协议保持可解析，退出码与诊断契约正确 |
| 导出期间写日志、日志不可用、目录选择取消 | 快照稳定、限制大小、取消不是错误；不能写出项目源码 |
| 生产构建堆栈 | build_id 可定位对应 source maps/符号，能还原已知失败位置 |
| 大项目与高频编辑 | 对比关闭/INFO/DEBUG 的操作耗时、日志增长与队列峰值；主线程无同步文件 I/O，不为日志复制模型 |

性能门槛先用现有代表性大项目建立基线，再确认可接受增量；不预先宣称“零开销”。日志级别与采样不能改变真实业务结果。

## 10. 实施前需确认的选项

本节给出完整建议，不代表已经修改产品策略。

| 选项 | 推荐方案 | 需要确认的理由 |
| --- | --- | --- |
| 日志基础设施 | tracing + 宿主共享支持 crate，engine 仅发事件 | 涉及工作区新增模块和依赖边界 |
| 默认保留 | INFO，10 MiB × 5，最长 7 天，应用总量受控 | 磁盘占用与排查窗口属于产品策略 |
| 默认信息范围 | 不含源码/字段值/完整参数，项目别名与脱敏相对路径，手动导出 | 决定排查便利度及导出内容 |
| 日志 UI | 主界面与欢迎页入口、错误详情、问题历史、打开目录和导出 | 需要确定具体入口位置与界面范围 |
| CLI 配置 | 显式日志参数，默认不创建持久日志 | CLI/CI 的存储预期不同于长驻编辑器 |

日志与错误契约确认后，实施以 P1 的正确性修复开始；上述建议参数可调整，不影响已确认问题及其修复必要性。
