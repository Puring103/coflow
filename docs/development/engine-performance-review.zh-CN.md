# 引擎数据结构与算法复审（2026-10-25）

审查基线：`e458a8f3e8f6acf0bc746c6d5565b611486bc7e2`。审查覆盖 language、model、checker、runtime、LSP，以及编辑器后端的写入、导航、查询和文件监听接入。测量均为无头 Release 程序，不包含前端绘制和 IPC。

现有不可变代次、记录值共享、按宿主分块的引用索引、实际读取依赖和事务分组方向合理。剩余优化应优先消除集中引用下的重复索引维护、嵌套修改的整棵值复制和每对象重复构建的 schema 索引；随后推进分页存储和字段槽布局。稀疏引用下的低延迟不能代替集中引用、宽对象、大集合和结构修改的验收。

本报告的性能改造项为后续实施建议，未计入已完成优化。既有十万条结果和未达标目标继续以[优化验收报告](../archive/benchmarks/engine-performance-optimized-2026-10-25.md)为准。

## 1. 新增拓扑基准

同一机器、Windows mimalloc、一次预热、每项三次采样。报告中位数，不据此验收 P95。原始样本、工作量和源码/二进制摘要见[拓扑测量 JSON](../archive/benchmarks/engine-performance-topology-2026-10-25.json)。

### 1.1 共同读取一个字段

每条记录有一个引用和一条 `next.value >= 0` 规则。环形拓扑每个目标只有一个读取者；集中拓扑全部记录读取第 0 条记录。每次更新第 0 条的 `value`，计时包含运行时修改和落盘；每组结束后独立完整重载并比较全部值、引用字段和诊断。

| 记录数 | 环形引用更新 | 集中引用更新 | 执行检查根：环形 / 集中 |
| ---: | ---: | ---: | ---: |
| 1,000 | 12.69 ms | 28.13 ms | 1 / 1,000 |
| 2,000 | 12.97 ms | 74.46 ms | 1 / 2,000 |
| 4,000 | 17.14 ms | 237.80 ms | 1 / 4,000 |
| 8,000 | 26.61 ms | 1,367.08 ms | 1 / 8,000 |

集中引用确实需要重新执行更多规则；这些额外求值不能省略。源码同时确认依赖索引维护还有额外的平方工作量，见第 2.1 节。两种拓扑的耗时差不是依赖索引耗时的独立归因，也不用于线性外推十万条延迟。

### 1.2 多个宿主引用一个目标

每条记录有一个引用，每批修改 10% 记录的普通整数字段，引用内容保持相同。计时覆盖借用输入组装和增量模型构建，输出析构与完整模型对照在计时外；保留旧快照，检查完整模型以及正反引用顺序。

| 记录数 | 批次记录数 | 环形引用 | 集中引用 |
| ---: | ---: | ---: | ---: |
| 1,000 | 100 | 0.121 ms | 0.149 ms |
| 2,000 | 200 | 0.251 ms | 0.366 ms |
| 4,000 | 400 | 0.551 ms | 1.034 ms |
| 8,000 | 800 | 1.181 ms | 3.317 ms |

源码中的逐宿主反复过滤入边列表解释了集中引用逐渐放大的成本。这项微基准与上一节的真实运行时提交范围不同，两组绝对时间不直接比较。

复现：

```powershell

target/release/examples/engine_model_topology_perf.exe
$env:AUDIT_SIZES = '1000,2000,4000,8000'
$env:AUDIT_SAMPLES = '3'
target/release/examples/engine_check_topology_perf.exe
```

## 2. 优先消除的重复工作

### 2.1 检查读者集合反复复制

位置：`crates/coflow-runtime/src/checks/read_graph.rs`，`CheckReadGraph::replace_rule/remove_rule`。

每条规则更新都先删除旧读集；删除一个字段的读取关系时，无条件克隆该字段完整的 `BTreeSet`，随后插回。H 条规则读取同一字段且共同失效时，会复制约 H² 个读者项，即使执行前后的读集完全相同。外层 256 个共享桶并没有消除这个桶内集合的重复复制。

建议按一批执行结果汇总新旧读集的差异；不变读集直接保留，变化的字段只对共享读者集合执行一次写时复制，再批量删除/插入。规则顺序、整个规则失效边界、失败查找依赖和未完成缓存规则保持一致。

验收：记录复制的读者项数和更新的关联数。固定依赖边数下，索引维护应接近读集变化量与首次复制量，不随共同读取者数量呈平方增长。高扇出求值本身仍按 H 条规则执行和计费。

另一个方向是全局规则：`CheckReadGraph::affected` 对每个变化字段再遍历该规则的整个读集寻找投影。一个规则读取 N 条记录、一次修改 K 条时，可产生 O(KN) 的影响分析，尽管最终只执行一次规则。反向索引可直接保存投影，或将规则读集按字段键分组检索；验收 100,000 条读依赖、1,000 条修改时不重复扫描完整读集。

### 2.2 反向引用逐宿主过滤

位置：`crates/coflow-model/src/indexes/relations.rs`，`RefIndexes::replace_hosts`；`build/incremental.rs` 的引用更新调用。

每个变化宿主都对旧目标的整个 incoming 列表执行 `retain`，然后重新插入边。B 个变化宿主共同指向拥有 H 条入边的目标时，产生 O(BH) 扫描。普通非引用字段变化也进入这条路径；十万宿主、1,000 条普通字段修改可触发约一亿次入边项访问，这一数字是循环次数推导，不是实测时长。

建议先比较引用相关字段或新旧宿主边块，引用没有变化时共享原块。确需改边时按目标归并变化宿主，一次过滤并合并新边。维度引用、拥有路径和宿主/块内顺序仍参与比较。

验收：统计被访问的 incoming 项和实际变化边；同一个目标每批过滤一次，最终正反引用及遍历顺序与完整构建一致。

### 2.3 嵌套字段修改提前深复制整个顶层值

位置：`crates/coflow-runtime/src/mutation/prepare.rs`，`materialized_top_level_value`；`cfd_loader/writer/patch.rs`，`field_patch`。

每个嵌套 `SetField` 都提前克隆整个顶层字段，再应用嵌套修改。writer 实际只在源码中缺少默认父对象、无法定位原路径时使用这份值。对于已经显式存在的长度 L 数组，B 次独立元素修改仍可能持有 O(BL) 个值副本。

当前 `CfdValue` 为 48 字节；1,000 次修改、十万元素的同一数组，仅这些元素的内联副本就约 4.8 GB，尚不含嵌套分配。这是布局和复制次数推导，不能当作实测进程峰值。

建议让准备阶段保存基线值借用/句柄与路径，只有源码定位确实需要物化默认父对象时才构造候选。多次修改共享同一顶层字段时，按原请求顺序维护一份覆盖结果。必须保留默认值实体化、父子路径、重复赋值和最早错误下标的语义。

验收：显式数组的 B 次元素更新，备用完整值复制次数为零；默认父对象最多按实际需要物化，不按每条请求复制。

### 2.4 每个对象重新建立字段索引

位置：`crates/coflow-runtime/src/cfd_loader/lower.rs`，`lower_object_fields`；`coflow-language/src/schema/queries.rs`，`CftType::field`。

降低每个记录和内联对象时，重新收集 `all_fields()` 为 `BTreeMap`。schema 已有字段名到字段序号的持久索引，可直接借用。该成本乘以全部对象数，覆盖冷加载及每个被重解析文件。

建议直接查询 `schema_type.field(name)`；重复源码字段的检测保留输入顺序，可以借用名称而不是复制字符串。名称构造接受 `AsRef<str>` 后，`RecordId::new(draft.id.clone())`、`TypeName::new(type_name.clone())` 等临时复制也可改成借用。

验收：每个对象创建 schema 字段映射的次数为零；诊断文本、顺序、位置以及保留可修复值的行为一致。

### 2.5 没有 data 规则的值也被完整遍历

位置：`crates/coflow-runtime/src/checks/planning.rs`，`insert_data_tasks` 及其值递归。

规划阶段遍历全部记录字段、数组、字典与内联对象，并创建路径；没有可达 data check 的类型也会承担这项成本。现有十万条夹具中的嵌套 `Stats` 没有 data check，仍被遍历。

建议在 schema 代次编译可达 data 规则的字段计划，类似现有引用字段计划。继承、多态和递归 data 类型需要固定点计算；只跳过能够证明没有可达规则的值。

验收：新增规划访问值数、构造路径数；没有可达 data 规则的标量数组和对象树不枚举元素，任务集合与执行顺序保持相同。

## 3. 存储布局与增量边界

### 3.1 局部修改仍有多个 O(N) 表操作

`coflow-runtime/src/load.rs` 每代汇总所有记录借用，再加入 builder；`coflow-model/src/build/incremental.rs` 进行全身份检查、分配 N 个惰性草稿槽、复制整张记录指针表、核对全来源，以及复制引用索引的两个 N 项顶层 Vec。模板依赖的两张 BTreeMap 也复制所有顶层节点。`runtime/src/indexes.rs` 的来源头部更新会触发整张共享指针表复制。

建议以分块持久表承载记录、来源和引用索引；惰性草稿按变化闭包或页面分配，输入使用源批次及变化区间。来源移动按被修改文件更新。页大小通过单条、相邻批次、跨页批次与完整遍历对照决定，不预设固定数值。

验收同时统计扫描槽位、复制槽位、草稿槽分配和原子引用计数操作。`records_materialized=1` 只能说明业务值重建量，不能证明整次修改是 O(1)。

### 3.2 对象字段仍有重复的树形布局

已验证名称使用 `Arc<str>` 可以降低克隆字节量，但不是按名称内容全局去重。每个对象仍保存自己的 `BTreeMap<FieldName, CfdValue>`；草稿又保存 String 键的树。字段访问需要名称比较、树遍历和节点间接访问。

中期方向是 schema 内紧凑类型/字段 ID 与连续字段槽，输入/输出边界映射名称。只读数据避免为每个标量增加单独的 `Arc`。字段遍历、序列化、诊断顺序、继承与多态、缺失及显式默认值信息必须单独保持。

这比删除重复字段索引的改动范围大，应在分配剖析与宽对象基准后实施。内存指标区分当前代次存活量、保留旧代次的增量量和分配器保留内存，不把进程峰值当作模型大小。

### 3.3 模板和维度的依赖精度

模板依赖在 `coflow-model/src/build/resolve.rs` 记录到记录级。许多模板只读取中心记录的 `name` 时，修改它的 `description` 仍会扩大到所有模板宿主；checker 的字段级读集已经更精确。

建议模板依赖记录字段/拥有路径与维度上下文，按实际结果变化继续传播。条件/缺失读取、引用改向和循环修复都需要完整登记。

维度输入每代重新构建绑定映射；已有变体的求值遍历受影响记录的全部字段。完整构建按上下文遍历全部记录和字段，维度投影切换还会把全模型转回草稿并重建。可缓存绑定、共享与上下文无关的值，按闭包构造投影。未直接标注维度的模板可能通过引用受影响，不能机械跳过。

### 3.4 健康增量和预编译计划

完整模型构建已使用 `ReferenceFieldPlan` 避免纯值字段的重复语义验证，但增量路径仍对受影响记录的全部字段进行额外递归检查；每次引用更新也重新分析整个 schema 的引用可达性。

建议按 schema 编译身份共享引用计划，健康增量采用相同的验证分工。只有来源位置变化、业务值没有变化时，直接共享模板与引用索引。带诊断的完整构建继续承担全部可修复值验证。

### 3.5 成员变化仍完整重建

新增、删除、重命名、排序和变体集合变化触发完整构建，是当前句柄与依赖契约下的明确边界。要把这些操作局部化，需要稳定槽位、代次或槽复用识别、独立展示顺序，以及成员/冲突组依赖索引；不能仅取消失效判断。

十万条高频编辑的下一阶段基准必须包含这些操作。单字段健康路径结果不能代表结构编辑、拒绝记录恢复或错误模型的延迟。

## 4. 宿主、集合与诊断

### 4.1 集合与求值路径

大字典继续保留有序条目；热点定位使用类型化键和可选辅助索引。`CfdRecord::value_at_path` 当前线性查找并逐项格式化键，大字典的重复定位会放大字符串分配。

check 的集合视图已借用多数模型值，应继续保留。`records(Type)` 仍会为每次表达式生成完整句柄 Vec，即使只取长度；可以按模型代次和类型共享有序成员视图。成员依赖与预算计量独立保留。

`containsValue` 在循环中重复克隆字典投影视图；对于保存变体名称 Vec 的维度视图，会产生 O(V²) 个名称引用复制。把视图移到循环外即可减少复制，并维持比较顺序和预算。量词的成功路径还提前构造绑定与路径文本，适合保留结构化上下文、失败时才渲染。

`coflow-checker/src/operations/builtins.rs` 中集合交集/不相交和子集/超集仍为 O(LR) 双层比较。可为相等性明确的标量域构建一次成员索引。数值提升、符号零、枚举别名、记录坐标及有限预算顺序必须单独证明，不能直接使用通用值哈希替换全部比较。

`isUnique` 已使用 `BTreeMap`，是 O(N log N)，不属于平方热点。保留第一次重复位置和枚举相等性；其剩余空间主要是字符串键借用与分配量，优先级低于上述平方路径。

### 4.2 文件与诊断分区

源缓存匹配和文本覆盖查找仍使用多层 Vec 扫描，并反复规范路径；文件数量大或一次覆盖很多文件时，宜按规范路径维护版本内索引。完整文件解析仍是源码更新成本的下界；进一步按记录解析需要独立设计恢复边界、位置迁移和文件级预算。

诊断密集时，相同源码校验仍要复制返回的完整诊断数组；变化更新还要物化诊断和来源索引。应以稳定诊断分区与共享内容减少内部复制，在协议需要完整输出的边界承担实际序列化成本。

具体而言，`coflow-runtime/src/checks.rs` 克隆上一代 `CheckDiagnosticStore`；其 `by_task` 是拥有诊断 Vec 的普通 BTreeMap，局部修改也会复制全部已有诊断，之后再次恢复完整输出。按规则/宿主共享诊断块，并为宿主建立诊断任务索引，可以减少缓存维护成本。输出 D 条诊断仍有 O(D) 的必要成本，不能承诺全部错误场景为 O(变化量)。

### 4.3 LSP 快照和查询

`coflow-lsp/src/validation/snapshot.rs` 每次快照重新发现 CFD 文件并读取全部关闭文件，再比较文本与 URI。缓存已避免未变文本的重复解析，但普通文字编辑仍有 O(全项目字节数) 的读取、分配与比较。

建议将 didChange 的文件身份和 watched-file 事件输入快照，文字编辑只更新指定来源；配置变化、监听丢失/溢出等明确状态执行重新发现和内容核对。不能仅用 mtime 与长度代替内容身份。保留未保存草稿优先级、任务合并和过期版本拒绝，可在阶段边界取消已过期任务。

定义索引的共享粒度仍是整个类型：`coflow-lsp/src/definition.rs` 的 `Arc::make_mut` 会复制该类型的全部记录映射，再替换文件内定义。十万条记录属于一个类型时，局部修改仍可能复制十万条索引头部。可采用分块映射、`FileId + Span`，并只替换真正变化的条目；文件行首索引已按文件建立一次，应保留。

引用补全每次复制、排序、去重全部可赋值记录 ID，并为所有候选生成协议对象。十万候选适合按前缀检索共享有序索引，按 LSP `isIncomplete` 协议继续返回；不能简单截断而使部分记录永远不可发现。

### 4.4 写入分组与发布

`cfd_loader/writer/batch.rs` 对真正独立的修改已实现初始/最终固定次数解析。重复路径、父子路径和影响缩进的补丁会形成 G 个顺序组，每组仍重新处理全文件及定位索引，成本可达 O(G×文件字节数 + G×文件记录数)。进一步优化需要在源码版本中维护局部编辑树与位置变化，按请求顺序验证；不能把多次赋值直接压成最后一次而丢失中间失败。

`writer.rs`、`session_build.rs` 与 `coflow-staging/src/lib.rs` 还分别持有源文本、覆盖文本、候选字节和回滚/冲突验证字节。适合统一不可变字节缓冲区与所有权移交，测量复制字节数。跨文件发布包含逐文件同步和完整内容核对，后续并行化必须保留原子回滚、失败归属与外部冲突规则。

### 4.5 宿主查询应先限制范围，再构造结果

`editors/cfd-editor/core/src/editor/session/graph.rs` 的 `start_records` 扫描全文件，并为每条记录构造全部引用结果，只为判断是否为空；之后才应用节点上限。BFS 到达折叠层时还先调用 `record_to_row` 构造全部字段再丢弃。

建议增加不分配的 `has_references`/引用迭代入口，起点在收集阶段就应用上限；折叠节点只构造需要的身份与诊断摘要。保留原始顺序、边集合和可用字段的范围语义。

`row_build.rs::snapshot_file_types` 对每个维度字段调用全量 `ref_targets`，再按文件/类型分组，成本乘以可赋值记录数。导航需要的是文件类型成员关系，可连接现有文件/类型计数与 schema 维度字段；普通字段更新不应再次枚举全部记录。`build.rs::type_navigation` 的整项目统计也可按成员变化维护。

`convert.rs::record_fields` 深复制所有字段值，并为每个值复制 schema 注解与摘要；大集合/宽对象应分别测展示范围和序列化量，优先共享 schema 注解、按请求范围生成字段数据。协议必须完整返回的值仍有必要输出成本，不能用省略用户可见字段获取速度。

### 4.6 宿主锁范围与缓存失效

`operations/data_queries.rs::get_ref_targets` 在写锁内读取设置、构造完整候选并复制缓存；命中缓存也复制整个候选 Vec。每次业务修改清空全部类型的候选缓存，普通无关字段修改也会使后续查询重建。

建议缓存绑定成员版本、缩略名字段版本和设置版本，基于不可变快照在锁外构造，提交时核对版本；查询支持范围/前缀。成员、类型、来源文件、缩略名和设置变化仍准确失效。

watcher 的模型候选已在锁外构建、旧代次也在锁外释放；但 `reload.rs::commit_data_reload_candidate` 仍在锁内构造 bootstrap，其中包含维度导航。普通 mutation 入口还在写锁内执行完整运行时修改、旧代次释放和诊断重建。建议把派生数据放入候选，在锁内仅核对版本和交换状态；写操作串行顺序与 publication/revision 绑定不能放松。

## 5. 正确性复核

### 5.1 独立补丁的中间结构预算

复现输入是同文件两条记录，各包含 450,000 个整数。第一条修改把 A 的数组扩到 600,000 项，第二条把 B 缩到 300,000 项。初始和最终均约 900,000 个节点，但第一步超过默认 1,000,000 节点限制。

审查基线上，单独执行第一条失败且不落盘；合并两条却成功。这是分组只解析最终候选导致的行为回退，已在本报告配套修复中纠正。

修复提交为 `daccc61a`。实现以实际解析后的旧、新子树节点差检查每个请求前缀。发生中间超限时，真实解析器重新解析该前缀，产生原来的失败下标和诊断位置；正常独立批次仍只解析初始与最终两份完整源码，单条写入不增加节点计数遍历。小预算回归比较完整顺序执行结果，覆盖同位字段插入与默认父对象实体化。百万节点公开 API 复测确认：先扩后缩在第 0 项失败且不发布，先缩后扩成功。

### 5.2 写入指纹的既有竞态

`editors/cfd-editor/core/src/editor/session/revision.rs` 的 `commit_internal_write` 在 runtime 发布后从磁盘重新读取内容作为内部写入指纹。若外部写入发生在发布与指纹读取之间，会把外部内容登记成内部内容；watcher 后续判定没有外部变化，模型仍保留内部版本。

已用真实 `RevisionCoordinator` 的确定性调用顺序验证这段合法交错：模型内容为 internal、磁盘内容为 external，连续两次 `has_external_change` 都返回 false。该行为在上一轮优化基线 `7e9d4fde` 已存在。本轮未调整此机制。

建议 runtime 将实际发布内容的摘要/缺失状态随结果传给宿主，避免发布后重新读取来建立期望。它同时消除一次额外磁盘扫描。读取 watcher 的实际内容仍保留，revision 票据和冲突保护也保留；mtime 不能替代内容身份。

## 6. 实施顺序与验收

| 顺序 | 范围 | 首要验收 |
| --- | --- | --- |
| A | 中间结构预算回归；后续修正内部写入指纹来源 | 请求顺序、失败下标、原子性、合法外部写入可见 |
| B | 读者集合差分更新、反向引用按目标归并、嵌套写入按需物化 | 集中引用索引工作量消除平方增长；嵌套批次消除 B×L 值复制 |
| C | 复用 schema 字段索引、引用/data-rule 计划、去临时名字复制、集合视图复用 | 分配次数、规划访问值数、冷加载与跨文件批次同步下降 |
| D | 分页记录/来源/引用表，字段槽，模板/维度细粒度依赖 | 固定变化闭包的扫描/复制量随变化页数增长，保留旧代次可独立读取 |
| E | 成员变化、宿主导航和 LSP 的局部维护 | 插入/删除/移动、诊断密集、草稿与外部修改的端到端验证 |

性能阈值继续保留完整加载 ≤5 s、普通单字段 P50 ≤50 ms/P95 ≤100 ms、跨 100 文件 1,000 次修改 ≤3 s 等原目标。新增集中引用、大数组元素批次、模板无关字段、维度切换、错误恢复和结构修改矩阵。先达到算法工作量指标，再用足够样本设定这些新增场景的延迟阈值，不从当前三次样本推断稳定尾延迟。

容器按用途选择：schema 布局和稳定句柄适合稠密/分块数组；短集合可保留线性遍历；大字典和关系集合采用辅助索引；需要确定顺序的结构继续保留顺序信息。并行化放在重复计算与复制收敛之后，避免用更多核和峰值内存掩盖平方算法。

## 7. 本轮验证

提交前修正编辑器流程测试的临时目录隔离：使用随机 `TempDir` 持有项目生命周期，避免多个测试进程复用固定目录；两份流程测试并发各 20 项通过，生产冲突检测保持完整内容比较。

预算修复后 `cargo check --workspace` 与 `cargo test --workspace` 均通过，共 718 项测试。新增拓扑基准均通过独立完整重建/重载对照。没有启动、停止或重启 CFD 编辑器。

十万条、100 文件的批次对照分别运行已提交基线 `e458a8f3` 和修复版 `daccc61a`，使用相同 Release 构建、mimalloc、独立子进程和夹具，每批三次采样。基线/修复版同文件 1,000 次修改中位数分别为 183.64/152.24 ms，跨文件为 5.35/4.32 s，全部通过独立完整重载对照，模型工作量保持 1,000 条重建、99,000 条复用和 4,000 个检查根。

本轮不同运行的耗时有明显波动，未修改的完整加载路径在这组对照也分别为 9.74/6.78 s；更早的修复版运行跨文件为 7.45–7.91 s。全部样本保存在原始 JSON。该复核未观察到修复导致明显退化，但不把串行小样本差值认定为性能提升，也不更新正式尾延迟验收。跨文件 3 s 目标仍未达到。


## 8. 重复工作收敛

检查读图保留未变化读集及其共享集合；读集变化时只维护新增、删除的字段关联。投影变化更新规则自身读集，影响查询使用当前字段的有序区间。集合首次写入采用写时复制，后续修改复用当前代次的独占集合，旧代次仍可独立读取。

反向引用按目标汇总整批宿主变化，每个目标的入边列表只过滤一次，再追加新边并恢复与完整构建一致的顺序。普通字段修改产生相同引用块时直接共享原块。

嵌套字段准备阶段验证路径并共享记录值树；源码能定位到元素时直接生成元素补丁，仅缺省父路径需要复制并修改完整顶层值。默认父值实体化、路径错误、逐步结构预算与事务发布保持既有规则。显式数组含 L 个元素、批次含 B 次元素修改时，准备阶段不再持有 B 份长度为 L 的数组。

CFD 对象降低复用已编译的 schema 字段索引，重复字段检测借用源码字段名。名字构造直接借用原字符串。字典 containsValue 在整次查询中复用值视图，维度变体列表只复制一次，求值顺序与工作预算保持不变。

回归覆盖高扇入引用批量改向与顺序、旧模型快照、检查读集变化与投影失效、延迟与直接实体化的源码文本对照，以及借用路径验证与原修改路径错误对照。性能基准包含完整重建或独立重载验证。
